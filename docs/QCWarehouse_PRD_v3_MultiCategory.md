> **最高优先级变更（阻断性）**：本文件完整取代《QCWarehouse 产品功能需求与验收规范 v2.0》中关于系统边界、服务分类、字段模型、模板设计与报告生成的定义。**QCWarehouse 是跨品类实物产品检查与样品对比平台；服装只是首批启用的品类。** 开发不得把服装字段、服装服务名称、尺码、衣物测量点或三件服装对比写入全局核心模型。v2.0 仅可作为首期服装 SOP 和运营细节的参考，不再作为系统架构依据。

## 00｜架构纠偏：本版本的不可妥协原则

1. **产品类别（Product Category）≠ 服务类型（Service Type）≠ 检查模板（Inspection Template）≠ 价格套餐（Offer / SKU）。** 四个概念必须在数据库、后端接口、后台配置和前端界面分离。
2. **平台核心与行业模板分离。** Order、Package、Sample、Inspection、Evidence、Report、Disposition、Shipment、Payment、Audit 等为所有类目共享；尺寸点、鞋底、五金件等属于品类模板。
3. **动态表单、动态检查清单、动态报告。** 同一个客户端下单页面和仓库作业页面根据启用类目及版本化模板生成，不为新类目复制一整套页面。
4. **开类目需要运营审批而非只改布尔值。** 技术上预留分类并不意味着 QCWarehouse 已具备检测能力。未上线类目不允许下单支付或显示为已提供服务。
5. **所有检查结果有方法与证据边界。** 人工目视与基础尺寸检查不等于材质鉴定、安全测试或正式认证；未检查项目必须可见。
6. **服装是首期实例，不是永远默认类目。** 即便首发仅有服装，实体表与 API 也不能出现 garment-only 的通用命名，如 garment_order、waist_measurement、leggings_report。
7. **修改配置不得追溯改变历史订单。** 服务报价、模板、阈值、报告字段在订单确认/任务创建时按规则保存快照，历史报告保留版本。
8. **系统仍然要小成本落地。** 采用受约束的配置驱动模板，而不是先开发复杂的通用表单设计器、插件市场或完整 ERP。

### 00.1 术语定义（开发必须统一）

| 对象 | 准确定义 | 示例 |
|---|---|---|
| Product Category | 分类树中定义的产品类别 | Apparel > Sportswear > Leggings |
| Service Type | 通用服务动作，不表达具体商品类型 | Single Inspection / Sample Comparison / Reference Matching |
| Inspection Template | 在一个品类上可执行的一组检查项与证据规则 | Apparel Basic Visual v1；Leggings v1 |
| Offer / Service SKU | 对外可购买的商业套餐、价格规则及适用范围 | Compare 3 Apparel Samples，$99 试价 |

| Report | 检查结论与证据的版本化展示 | RPT-…-v1 PDF/网页 |
| Capability | 运营具备并准许对外承诺的检查能力 | 目视检查；基础卷尺测量 |

## 01｜业务定位与范围

### 01.1 对外描述

**QCWarehouse helps overseas buyers inspect and compare physical product samples in China before international shipping.** It provides structured visual checks, measurements where applicable, side-by-side comparisons, evidence-based reports, and optional sample handling. Available checks depend on the product category and selected service.

对外宣传平台是 **Product Inspection & Sample Comparison**，不可整体定位为 Garment Inspection Only。首页可以突出“首期提供 Apparel Inspection”，但页头、数据库和业务核心不得写成服装专属系统。

### 01.2 目标客户与首期经营

- 海外独立零售商、Shopify 店主、初创消费品品牌、Whatnot/TikTok Shop 转售商，以及自己在中国采购样品的个人买家。
- 客户自行向工厂、1688、淘宝等卖家购买产品并寄到 QCWarehouse，平台不代表客户签采购合同或垫付货款。
- 主交付是检查证据与报告。样品可按约定留存、国内转寄至客户集运仓或代为执行授权退货寄件，不承诺原卖家退款。
- 首期以服装试运营，后续类目扩展按设备、检查方法、SOP、责任边界和试单能力决定，而不是靠销售页面直接开通。

### 01.3 明确不做

不做工厂现场生产巡检、AQL 大货抽检、假冒鉴定、完整产品认证、化学检测、带电安全认证、面料纤维真实成分鉴定、代购和售后谈判；需要具备资质的实验室项目只能先做真实合作与适当标注，不得自动当作自营能力。

## 03｜产品分类、能力与上架治理

### 03.1 类目树示例（仅结构，不承诺开通）

| 一级类目 | 二级示例 | 初期状态 | 服务能力 |
|---|---|---|---|
| Apparel 服装 | T-Shirts / Leggings / Sports Bras / Dresses | ACTIVE | 目视、尺寸、指定细节、样品对比、确认样对照 |
| Footwear 鞋履 | Sneakers / Casual Shoes | PLANNED | 待建立鞋类 SOP 与量具 |
| Bags & Accessories 箱包配饰 | Handbags / Backpacks | PLANNED | 待建立结构、拉链、五金模板 |
| Home & Lifestyle 家居日用品 | Textiles / Decor / Simple Accessories | PLANNED | 不同子类目评估后开放 |
| Consumer Electronics 电子产品 | Basic accessories / Devices | RESTRICTED | 不承诺通电、性能、电气安全等检测 |
| Toys & Children’s Products 玩具儿童用品 | Toys / Child accessories | RESTRICTED | 安全法规与材料风险高，须专项评估 |
| Cosmetics & Food Contact 美妆与食品接触用品 | — | RESTRICTED | 不提供成分、安全与法规认证 |

### 03.2 类目字段

category_id、parent_id、slug、display_name_en/zh、description、status (PLANNED/ACTIVE/PAUSED/RESTRICTED/RETIRED)、allowed_service_type_ids、capability_requirements、excluded_claims、documentation_url、sort_order、effective_at、version、created_by、approved_by。

### 03.3 类目启用守卫（必须后端强制）

类目从 PLANNED → ACTIVE 必须通过：①模板已发布 ②对应员工已培训 ③设备与量具已确认 ④服务边界与免责声明通过复核 ⑤价格、工时、物流限制已设定 ⑥演示样品完成内部试运行并有报告样本。任何一项未满足只能展示“Not available yet / Contact us”，**不得创建可支付订单**。

## 04｜服务类型与品类模板的组合

### 04.1 全平台通用服务类型

| 服务类型 | 通用流程 | 品类层应配置的内容 |
|---|---|---|
| Product Inspection（逐件标准检查） | 按委托数量1到N件逐件收样→识别→检查→证据→报告 | 具体检查项目、量测点、必要照片、限值规则 |
| Side-by-Side Sample Comparison | 多样品归组→同条件检查→差异报告 | 可比较的项目、同类同规格匹配规则、差异单位 |
| Reference Sample Matching | 绑定确认样→新样检查→差异报告 | 参考样保存要求、关键指标与适用公差 |
| Additional Evidence Capture | 指定局部照片/视频/重量等 | 哪些拍摄/计量能力已获得批准 |
| Domestic Sample Handling | 暂存、留样、转寄、退货寄件 | 危险品、尺寸重量、保存和快递限制 |

这些服务只是“动作类型”，不能未经类目审查向任何产品开放。例如“电子产品检查”不能自动继承服装的全部单件检查项目。

### 04.2 商业报价与能力矩阵

外部 SKU 与模板并非一对一：一个服务 SKU 可以包含多个模板子章节，也可以根据类目、复杂度和数量选择不同价格。但必须记录 SKU、报价快照和所需能力：

```text
Product Category + Service Type + Template Version + Quantity + Options
  -> Eligibility / Capability Check
  -> Offer/SKU Match
  -> Pricing Quote (snapshot)
  -> Order Confirmation & Payment
  -> Inspection Task (template snapshot)
```

不能出现 `if category == 'apparel'` 贯穿支付、报告、存储层；只允许在模板适配器或特定计算/验证器中存在品类特殊逻辑。

## 05｜配置驱动的检查模板引擎（核心）

### 05.1 检查模板的数据结构

模板应包含 template_id、category_id、service_type_id、name、version、status、effective_at、created_by、reviewed_by、default_method、applicable_attributes、inspection_items、required_evidence、comparison_rules、report_sections、limitations。内部字段定义为受控 JSON schema/数据库结构，不允许任意可执行 JS；字段变更需有版本管理。

### 05.2 检查项元数据

每个 `inspection_item` 最少包含：item_id（永久稳定标识）、display_label_en/zh、section、input_type、unit、precision、required、applicable_when（受约束条件）、acceptable_values / optional_tolerance、method_id、evidence_requirement、help_text、order、claim_boundary。支持：短文本、数字、枚举、布尔、日期、照片/视频、带单位测量、差异标注、NA/无法判断；特殊判定规则由后端白名单验证。

> 测量必须记录 **单位、工具、测量方法、是否拉伸或施力、精度/公差来源**；未经客户提供技术规格与允许偏差，系统不得自动认定“未达标”。

### 05.3 通用检查模板中的基础章节

1. **Identity & Packaging**：商品名称/型号/变体、实收数量、外包装外观、标签或序列标识（按类目适用）。
2. **Visual Condition**：外观、破损、污渍、颜色差异、明显工艺缺陷（按类目定制词典）。
3. **Measurements**：尺寸、重量或计数（仅在类目和设备许可时使用）。
4. **Components & Accessories**：拉链/钮扣/鞋带/电源配件等“组成件”，由模板配置。
5. **Comparison**：与同类样品或确认样对比的项目及证据。
6. **Limitations & Not Tested**：未检查或超出能力范围的风险与限制。

### 05.4 状态、差异与异常（通用）

- 结果状态：RECORDED（已记录）、OBSERVED_ISSUE（发现需关注的现象）、NOT_OBSERVED（在限定方法下未见）、NOT_TESTED（未测试）、NOT_APPLICABLE（不适用）、BLOCKED（条件不满足）。
- `NOT_OBSERVED` 不能映射为“产品合格”；“目测未发现”不等于“质量保证”。
- 样品对比只对同一种或被运营批准的兼容类别生效。不同款型、材料、尺码时在报告中明确比较局限。
- 视觉色差使用指定照明与拍摄方法，不输出未经仪器测量的 ΔE；实际重量不能自动宣称面料 GSM。

### 05.5 模板版本与审计

模板：DRAFT → IN_REVIEW → APPROVED → PUBLISHED → DEPRECATED/RETIRED。发布后不可就地修改历史版本；新版本应克隆并再次审查。已支付订单保留服务/报价快照；已开启的检查任务保留模板快照。发布报告要包含 `template_id + version + executed_items`，后续改模板不得改动历史内容。

## 06｜首期模板：服装 Apparel（不是平台核心字段）

首期仅开放服装类目的三种通用服务：按件标准检查（1至N件）、同类样品比较、确认样对照。可以从 T 恤、瑜伽裤、运动内衣做首批检查模板，原因是有既定基础设备与 SOP，并非系统限于服装。

### 06.1 Apparel Basic Visual v1

- **元信息：** 产品款号、申报颜色、申报尺码、面料标签信息（仅记录声明，不代表成分鉴定）。
- **照片：** 正面、背面、尺码标、洗标、重点缝线/瑕疵局部；服装款型不支持某角度时可标 NA。
- **基础指标：** 衣长、胸宽、腰宽、袖长等依子模板出现，单位 cm；需标明测量点/平铺条件。
- **工艺：** 跳针、断线、漏缝、拼接不齐、印花与标识外观、污渍或破损。
- **不测：** 纤维含量真实百分比、成衣洗后缩水、色牢度、耐磨、皮肤安全、标准认证。

### 06.2 Apparel > Leggings v1

字段由服装模板扩展：平铺腰口宽、臀部指定点、前裆/后裆、裤长、内长、大腿宽、脚口宽；拍摄量尺示意，比较尺码相同与否；左右对称性、腰部缝线、印花、明显外观瑕疵。未经标准化实验不能承诺“绝不透光”“永久不变形”。

### 06.3 Apparel > Tops v1

尺寸：衣长、胸宽、肩宽、袖长、袖口宽、下摆宽；依款型适用。重点检查领口、门襟、扣眼、侧缝、印花与绣花，不适用字段必须显式写 NA 而不是空白。

### 06.4 Apparel > Sports Bra v1

尺寸：平铺下围、前片高、肩带长度/位置、背部结构；配件：可拆胸垫有无与左右一致性。不得仅凭视觉承诺支撑等级、适合某种运动、穿着舒适或医疗功效。

### 06.5 后续类目“影子模板”示例（不可销售）

**Bags Basic Visual DRAFT：** 长宽高、拉链开闭外观、提手缝线、金属配件外观、内衬、包装。**Footwear Basic Visual DRAFT：** 尺码/鞋长、左右一致性、鞋底与外观粘合状态、装饰件、包装。此两类可以在开发测试环境模拟一次“配置新类目→订单→检查→报告”，但是生产环境必须维持 PLANNED，不显示购买入口。

## 07｜客户界面与动态下单

### 07.0 注册与账户（用户已确认）

首发采用 **Google / Microsoft一键注册登录，并保留邮箱验证码备用**。页面必须实际支持Gmail与Outlook个人账户，不只放两个按钮或限制两个邮箱后缀。微软工作/学校账户另行验收后开放；不同登录方式连接至同一平台用户，不能仅凭相同email自动合并。

首次验证身份、必要的通知邮箱及平台注册条款后，原子创建账户、个人组织、永久专属收件码，展示后台默认仓址。后续登录、换邮箱、连接另一provider都保持原码、订单及物件归属。第三方标识使用供应商稳定subject；通知邮箱是可验证、可变更的联系方式。Google/Microsoft登录仅申请必要身份信息，不读取客户邮件。

客户安全页须支持连接/解除登录方式、换邮箱、设备会话、最近重新认证、无法登录时恢复；不能解除最后一种可用登录方式。恢复须身份核验、独立审批和审计，专属码/单号不能单独作找回凭据。限制/注销账号不清除仍在仓商品或未结账务。详细schema/API/异常态、正式配置与测试见开发规格§21。

### 07.1 信息架构

### 07.2 六步下单向导

1. **Select Product Category**：显示启用类目；未启用类目可查看范围但不得进入支付，允许留下需求咨询。
2. **Choose Service**：仅展示此类目已批准的按件检查、样品对比、确认样对照或可用附加项。
3. **Enter Product Details**：按分类动态加载属性；服装有尺码颜色，箱包则是型号规格，不能给所有类目强制 `size`。
4. **Select Inspection Items**：展示模板默认项目、允许的额外照片与可加价项目；禁用不支持的检查项。
5. **Confirm Quote & Terms**：明确样品数量、价格、预计工时、收货与保管条件、无法提供的认证/测试。
6. **Pay & Send Samples**：账户专属收件码与后台默认仓址在注册后即可复制，用于向商家购物及登记原始物流单号；Stripe确认质检费后建立本单委托位置，识别实物后建立对应检查任务；真实物件在入仓时建档并绑定已有/后补订单行，不能因后付费重复建实物。账户码、委托位置与物件编号分开，支付失败不可进入已付状态。

### 07.3 动态字段校验

- 商品属性存储为 `category_attributes`，由分类 schema 限制类型、长度、允许枚举和必要性；严禁一个共用文本框收纳全部重要字段。
- 同类对比可要求同规格或标记“比较受限”；不允许跨类目直接比较并自动生成结论。
- 动态表单的英文/中文显示名来自同一个字段定义；用户端不出现未翻译的内部 ID。
- 客户可上传参考图与商品链接，不自动爬取受限站点或将卖家链接解释为真实合格标准。

### 07.4 下单页面验收

服装类目可完整付款并流转；箱包类目可显示未来说明但不可购买；新增箱包测试模板只需后台发布配置、不修改通用下单页面代码；弃用模板后历史订单仍能查看原始表单与报价。

### 08.2 关键约束

- `category_id` 与 `template_id + version` 在检查任务创建时固定；对错类目样品必须暂停并由客户确认修改方案，不允许检查员直接悄悄覆盖。
- 测量值用 decimal/numeric 并声明精度与单位；金额用整数最小货币单位并保存币种，与实施规格及Stripe一致；单位标准化，不以自由文本单位直接用于计算。
- `typed_value` 与 `result_status` 成对存储，缺值要说明是 NOT_TESTED、NOT_APPLICABLE 还是数据遗漏。
- 同一照片/测量值可被多个报告引用，但原始证据不能因删报告而消失；报告下载权限由组织/授权共享策略控制。
- 可在 `samples.category_attributes JSONB` 存灵活元数据；但样品 ID、类别、组织、任务、订单关系等关键索引为强类型关系字段。不能把所有业务对象塞进一个 JSON。

## 09｜订单、包裹、样品、检查与报告状态机

| 对象 | 主状态链（可有异常分支） | 必须具备的守卫 |
|---|---|---|
| Order | DRAFT → QUOTED → AWAITING_PAYMENT → PAID → AWAITING_SAMPLES → IN_PROGRESS → REPORT_READY → DISPOSITION_PENDING → CLOSED | 支付 webhook 验证；报价快照；未启用类目不可创建有效报价 |
| Package | PRE_ADVISED → DELIVERED_UNVERIFIED → CHECKED_IN → CONTENTS_MAPPED → STORED → DISPATCHED | 未认领包裹不能关联错误组织 |
| Sample | EXPECTED → RECEIVED → IDENTIFIED → READY → INSPECTING → INSPECTED → STORED/OUTBOUND | 身份不符需隔离；任何物理出库需授权 |
| Inspection Task | PENDING → READY → ASSIGNED → IN_PROGRESS → SUBMITTED → QA_APPROVED | 缺强制检查项、照片或方法信息不能提交 |
| Report | DRAFT → REVIEWED → PUBLISHED → SUPERSEDED (仅在修订时) | 修订发布新版本，不覆盖历史文件 |
| Disposition | REQUESTED → VERIFIED → FEE_CONFIRMED → APPROVED → PACKED → SHIPPED → COMPLETED | 地址、收件信息、危险品限制和客户授权 |

异常分支：ON_HOLD / NEEDS_CUSTOMER_ACTION / CANCELLED / FAILED / CLAIMED/UNCLAIMED（包裹）；退款（Refund）是独立财务对象，不能用订单状态代替财务事实。

## 10｜仓库通用 SOP 与各品类适配

### 10.1 所有类目的通用 SOP

①客户预报包裹与样品→②到仓拍摄外包装/运单→③核对并编号→④记录申报类目与实物是否一致→⑤按设备和场地安全分区存放→⑥任务分配与模板核验→⑦执行检查并采集证据→⑧第二人或独立规则复核→⑨发布报告→⑩依逐样授权出库/留样。每一步都绑定时间、操作者、样品 ID 与必要证据。

### 10.2 动态工作台要求

检查员进入任务时看到该类目的 **检查步骤、图片要求、量具说明、异常词汇、不可承诺项**。不能在所有品类显示“腰围、胸围、前裆”等服装字段。每项记录必须能直接定位关联照片；离线暂存可作为后续能力，但一旦上传失败不能误报已提交。

### 10.3 不同品类的实体作业差异

- 服装：洁净台面、平铺量尺、统一背景、服装瑕疵标准、服装包装回收。
- 箱包（未来）：支撑展开、五金及拉链观察、三维尺寸、包装防压；新的 SOP 培训后启用。
- 鞋履（未来）：左右脚标签、尺码、外观粘合检查、鞋底/鞋面照片；未经资格不得做耐折、耐磨性能结论。
- 电子产品（受限）：仅可在能力评估后提供极有限的外观与配件核对；电池、通电、绝缘及运输有额外风险。

### 10.4 样品保管和处置

标准质检按委托件数逐件作业，覆盖一件、几件和几十件。所有类目共享样品库位和授权系统，但库存条件/危险品属性由类别和样品属性限制。客户可逐件选择保留确认样、国内寄往集运仓、国内退货寄件或其他已支持的去向；客户自行办理原采购退款争议。

**退货寄件的分工**：客户自行向原商家申请退货，获得并提交商家指定的退货收件地址，确认由自己承担寄回运费。仓库按授权地址打包代寄，寄出时由仓库填写承运商和实际退货快递单号，客户可在订单内复制该单号反馈给商家。客户提交地址时无须提供快递单号。

### 10.5 物流闭环与双语轨迹（首发必须）

客户登记商家发货运单后即可在账户查看英文完整轨迹，无须先建立质检订单。仓库退商家、寄集运仓或国内转寄时，填写真实寄出运单后自动建立另一段跟踪。后台显示中文原始物流信息，客户显示英文状态与事件、最新更新时间、异常提示和需要补充的资料。

默认技术方案是快递100企业查询/订阅API，尚未开通或验收；正式适配器、频控、电话验证、回调验签、重放、错单修订与双语失败降级以[开发规格 §19](开发规格.md#19-全程物流查询与中英文展示r1-必须交付)为准。录入运单只是开始，不能把可复制单号当成物流功能交付。英文暂不可用必须明确提示并保留最新已知状态，不能编造翻译。

承运商签收、仓库实际验收入库、质检完成、仓库出库交接、商家退款是不同事实，禁止自动互相替代。送至集运仓只表示国内段，不代表海外最终交付。运输异常、供应商故障、无记录、校验电话缺失、承运商不支持都要有明确UI与待办。订单关闭后未结束运输继续跟踪。

### 10.6 多件合包与拆包（首发必须）

客户可逐件选不同去向，同一客户跨订单商品可经明确授权合包，同一批次可拆多个实际包裹；不跨客户自动合包。每包独立运费明细、运单及轨迹，处理费按公示规则计一次。地址、商品清单、报价、支付及逐包扫描必须一致，已付修改须冻结并重报价。退货由客户先向商家申请、提供退货地址，仓库代寄回填单号，运费客户承担。详见开发规格 §20.1。

### 10.7 无订单实物、盘点与异常处置

入仓即逐件编号并保留包裹、位置和证据，无主/未委托/部分映射状态明确。后续客户付费绑定委托，不创建第二份库存。基础盘点、并发移位冲突、差异冻结/找回与独立库存调整属于P0；丢损事件要区分服务退款与商品赔偿，不自动突破已收款可退余额。

超期或禁限品进入异常队列，由责任人核对允许的退回/处置方案。任何报废执行须有精确清单、有效依据、独立审批及实际留证，不能仅凭超期自动清库存。详细目标见开发规格§22.3–22.5。正式处理政策未确认时保留人工受控流程并关闭生产销毁执行。

## 11｜证据系统与报告引擎

### 11.1 统一报告骨架

1. Cover：QCWarehouse、报告 ID/版本、检查日期、服务类型、产品类别。
2. Scope：本单实收样品、委托检查范围、适用模板/方法与未检查项目。
3. Sample Identity：样品 A/B/C/确认样编码、型号、申报属性、到仓状态。
4. Inspection Results：模板驱动的检查章节、记录值、单位、方法和照片证据。
5. Comparison：仅有对比服务时生成差异表；字段来源于同名 `item_id` 的兼容检查项目。
6. Exceptions & Observations：异常、差异、客户需确认事项。
7. Limitations：样品代表性、目视检查限制、未做实验室测试等。
8. Audit：执行人/复核人、时间戳、版本号、校验码或可验证链接。

### 11.2 报告生成规则

报告引擎不得依赖 apparel 专用 HTML 模板才能运行；共用母版动态插入模板章节。不得在鞋包报告出现服装术语、空腰围表、GSM 声明等。所有未记录的必填项阻止发布；Not Tested、Not Applicable 必须在适当位置显式显示。数字比较要求单位兼容；不兼容需标记不可直接比较。

### 11.3 发布后修订

发现误写：创建修订版本（v2），列出修订原因及差异；旧版保留在审计及授权可见历史中。二维码与分享页面始终指向带版本校验的授权资源，不允许公开裸露客户资料或无权限照片。

## 13｜后台：类目、模板和商业运营配置

运营后台需要类目管理、能力管理、模板管理、报价套餐管理、样品/库位管理、订单异常处理、复核报表与审计。每个配置对象都有草稿、预览、复核、发布、停用机制。运营可在无代码改动下新增“箱包基础目视检查”草案和演示报告，但**生产上线需审批清单并由管理员确认**。

权限角色：客户、收货员、检查员、复核员、客服、财务、平台管理员、内容/模板管理员。模板发布/开放新类目至少需要与日常执行有分离的批准角色；财务、客户敏感资料遵循最小权限。

## 14｜接口入口

所有本站接口使用 /api/v1。交易写入、报价及运单读取以 [交易 OpenAPI](contracts/core.openapi.yaml) 为准。其余端点和权限、错误语义见[开发规格 §7、§19–22](开发规格.md)。复核、PDF生成和报告发布依次执行，最终发布由服务端作业完成。

## 15｜非功能要求、安全与可维护性

- **多租户隔离：** 客户只能查询本组织订单、样品、照片与报告；分享链接应有权限、到期和撤销机制。
- **对象存储：** 原始证据私有；下载使用短期签名 URL，保存校验和；报告文件不可静默覆盖。
- **审计：** 状态变更、检查结果修改、模板发布、报告修订、退款及出库审批记录操作者与时间，普通人员不能删除。
- **幂等：** 支付 webhook、物流入库扫描、报告发布和通知重试不能制造重复交易或重复出库。
- **数据最小化：** 不长期保存银行卡敏感信息；保留和删除周期经服务协议与适用法律确定，客户图片/供应商资料不得默认用于模型训练。
- **国际化：** 客户英文优先、运营中文；数据库字段用稳定 code 而非依赖翻译字符串；时间 UTC 存储、用户时区展示。
- **可监控性：** 日志不暴露客户地址与敏感订单内容；对丢件、支付失败、报告生成失败建立告警。
- **兼容性：** 同一个客户端路由、下单状态机、报告框架必须可运行第二类目影子测试，不修改通用模块。

恢复必须先隔离外发、核对资金与真实交接、失效旧会话/认证挑战、重放注销/删除/撤销清单，不能用恢复旧队列再次退款或出库；实测恢复目标及证据见开发规格§22.6。

## 16｜开发顺序与上线门禁

### Phase 0：架构与样品定义（先完成）

确认多品类实体和模板规范；做两份夹具：**Apparel Leggings ACTIVE** 和 **Bags Basic Visual PLANNED**；在开发环境让两类分别走完整检查流程，生产只允许 Apparel 购买。

### Phase 1：轻量 MVP

注册/登录、分类服务目录、动态下单/试价、Stripe支付状态、物流预报/中英轨迹/入仓、动态检查模板及审批配置、证据上传、英文报告与版本化PDF、逐件处置和合包拆包、中文后台、异常通知、审计。上线后测试 10–30 笔真实服务订单并统计工时、报告返工、收件错误、客户异议、单笔贡献利润。

### Phase 2：流程优化

更多服装子模板、复杂模板设计器、审批效率优化、营销邮件、扫描与库存优化、额外证据套餐、统计面板。基础模板审批发布、必要交易/异常通知及版本化PDF均属于Phase 1，不能借本阶段后置。

### Phase 3：非服装类目上线

按客户需求、合规风险、设备/培训、定价及试单结果依次开放箱包、鞋履或其他低风险产品。每个类目须单独经过运营验收；系统的架构支持扩展不意味着业务对外先行承诺。

## 18｜从 v2.0 到 v3.0 的变更映射（开发必读）

| v2.0 易误导位置 | v3.0 强制修正 |
|---|---|
| “Garment Check” 作为通用服务名称 | 使用 Product Inspection；单件是数量为1的场景，服装版只是一个服务套餐 |
| 服务价格直接按服装写在流程核心 | 报价引擎按 Category × Service × Template × Quantity × Options 计算 |
| “服装检查项目矩阵”被理解为系统字段 | 降为 Apparel 模板定义，不得进入核心 SQL 列 |
| 下单默认瑜伽裤、尺码、颜色 | 第一步选品类，属性按 schema 动态渲染；无通用必填尺码 |
| 报告默认服装尺寸表与缝线项目 | 通用报告母版 + 品类章节；服装表仅该模板启用 |
| 仓库工作台固定量尺和拍照角度 | 由模板返回检查项、方法与拍摄清单 |

## 19｜负责人需要确认的少数事项（不阻塞通用架构）

- 首期服装服务选哪几个正式套餐、试价是否按前版 $29/$99/+30/$39–49 验证；其他类目价格不得复制。
- 本地仓库在营业执照、场地与安全条件下允许接收哪些商品；含电池、液体、食品接触和儿童用品默认不收。
- 每种样品的默认保管期限、收费及到期后合法处置政策。
- 已批准的支付商户资格、付款方式、服务收入入账及退款责任。
- 首发报告保留期限、分享链接策略、客户数据保存与删除义务。

- 物流账号与额度、HTTPS回调、首发承运商覆盖及面单验证电话；正式数量档/产能交期和未委托实物保管规则。

- 自有Google/Microsoft正式登录应用、个人账户类型、回调域名；交易邮件账号/发信域名及实际投递，赔偿原则及异常处置执行依据。
