# QC Warehouse 开发规格

履约实施参考 **v2.7** · 2026-11-04 · 架构与功能基线见 [PRD v3.2](QCWarehouse_PRD_v3_MultiCategory.md)。领取任务前阅读 [协作入口](../AGENTS.md) 与 [功能排期](开发排期与任务台账.md)。本文件描述目标行为；实现进度只看任务台账。

## 0. 本文使用说明

### 0.1 目的

产品架构、功能优先级和上线门禁以 [PRD v3.2](QCWarehouse_PRD_v3_MultiCategory.md) 为准。本文件保留注册收件、按件质检、Stripe、仓储、退货及首期服装 SOP 的实施细节。

**实施基线**位于 §4.2 和 §7。产品范围按 PRD v3.2，开发任务和验收证据按台账。开工时由 TASK-002/152/166/163 将本次设计基线转为版本化工程迁移、DTO 和服务层测试。§23 登记跨模块验收、上线前置和变更规则。

### 0.2 约定

- **`[DEFAULT]`**：我为了不阻塞开发而设定的默认值（价格、SLA、保管天数等）。全部放在配置或种子数据里，业务可以改，**不改代码**。
- **`[DECIDE]`**：必须由业务方决定的事项。本文已给出不阻塞开发的实现方式，决策清单见第 18 章。
- R1 交付客户自助订单全生命周期；R2 与 R3 只按附录 B 指定的阶段开放。
- **金额**：整数最小货币单位（美分），币种 USD，R1 只支持 USD。
- **时间**：数据库一律 `timestamptz` 存 UTC；客户端按浏览器时区和中国时区（Asia/Shanghai）各显示一次。
- **ID**：内部主键 UUID v7；对外订单号 `QW-` 加 8 位 Base32（去掉易混字符）；样品码 `S-` 加 6 位；包裹码 `P-` 加 6 位。外部编号一经生成**永不复用**。
- **规范用词**：MUST 必须；SHOULD 建议；MAY 可选。

### 0.3 范围边界

QC Warehouse 提供寄仓后的产品质检。客户向商家购买商品时填写自己的专属收货信息，卖家发货后登记原始物流单号。仓库扫码或搜索运单即可定位客户及已关联的质检单。标准质检覆盖一件、几件和几十件商品，按委托件数逐件检查；另有可选的同类样品横向对比服务。报告发布后由客户决定寄往集运仓、国内地址、退回商家或继续保管。商家货款由客户自行支付；平台通过 Stripe 收取质检与履约费用。

| 范围 | R1 | R2 | R3 |
| --- | --- | --- | --- |
| 服务类型 | 标准逐件质检（1 到 N 件，含几十件）、独立同类横向对比（2–3 件）、确认样对照基础能力 | 更多已获批组合与附加项 | 新服务按准入评审 |
| 品类 | apparel；具体子类模板须通过 PRD 准入，样例定义不等于可销售 | 追加已审批服装子类 | 新品类包 |
| 处置 | 逐件授权、合包/拆包、国内/集运仓/退商家、续存、报价收款、录单交接与自动物流查询 | 扩展仓储优化 | 预约取件/电子面单接口 |
| 支付 | 香港公司；Stripe Checkout，检查费、寄件费、续存费独立 | 优惠码 | 多币种 |
| 报告 | 在线报告、版本化 PDF、英文内容复核与基础只读分享 | 批量报告导出 | 白标 |

**明确不做**（任何阶段都不进本系统）：代购、垫款、与卖家谈判、代申请退款、厂验、实验室检测、自动 AI 质量结论、抓取 1688 或淘宝订单、订阅会员。

### 2.3 通用工程规则

1. **所有写操作走服务层函数**，在一个数据库事务里完成状态变更、审计事件、待发通知（outbox）。接口层不直接改表。
2. **状态变更只能通过状态机函数**（第 5 章），禁止直接 `UPDATE ... SET state`。
3. **幂等**：支付回调、出库、收货扫描等接口接受 `Idempotency-Key`，在 `idempotency_keys` 表去重。
4. **价格由服务端计算**，客户端传的金额一律忽略。
5. **未知入仓媒体暂存 staff-intake/{captureId}/{mediaId}，仅授权员工可访问，认领后在事务中建立归属；客户对象存储 key 不含客户信息**，格式 `org/{orgId}/order/{orderId}/{mediaId}.{ext}`，访问一律签名 URL，有效期 10 分钟。
6. **错误响应格式**统一：`{ "error": { "code": "ORDER_NOT_PAYABLE", "message": "...", "details": {} } }`，`code` 用稳定的大写蛇形，前端按 code 映射文案。
7. **审计**：所有后台与仓库写操作、所有状态变更、所有权限拒绝都写 `audit_events`，该表只允许追加。
8. **配置化**：价格、SLA、保管天数、复测阈值、禁用词、品类开关都从 `app_config` 或品类包读取，不写死。
9. **测试订单**：`orders.is_test = true` 的订单不计入统计、不发真实邮件（发到测试收件箱）、不走真实支付。

### 2.5 国内网络与仓库端约束

- 仓库端 `/wh` 路由**不得**引用外部 CDN 脚本、Google 字体或境外第三方登录；字体与脚本构建时打包自托管。

- 上线前验收：用仓库实际手机，在 4G 与宽带两种网络下一次性上传 30 张照片，中途断网再恢复，不丢数据、不重复。

## 3. 品类、服务与模板配置架构

### 3.1 通用模型

产品类目树、通用 service_type、获批 capability、不可变 template_version、可售 offer/SKU、订单行独立建模，以 PRD §§03–05/08 为准。一张订单可以含多个类目的 order_lines，每行锁定类目、服务、模板、数量、选项与报价。标准逐件检查支持1到N件；同类对比组2–3件，跨类目不得直接作差。确认样匹配引用客户授权且有效的参考样。

### 3.2 品类包与模板后台

仓库内 apparel 配置是导入种子和版本归档，不是唯一配置入口。R1 后台支持受控字段编辑、草稿、预览、校验、提交审核、独立批准、发布、停用。复杂拖拽设计器后置；禁止可执行脚本。编辑模板不得修改已发布版本，新订单引用新版本，旧订单和报告保持原快照。

类目状态统一 `PLANNED/ACTIVE/PAUSED/RESTRICTED/RETIRED`；模板状态按 PRD 的生命周期。类目只有 ACTIVE 且能力、SOP、人员培训、设备、报价与试运行材料完整才可售。前端、报价、提交和支付前使用同一后端资格守卫，前端隐藏按钮不能代替守卫。

### 3.3 版本化资源

| 资源 | 内容与使用方 |
|---|---|
| order_form.schema | 对应类目/套餐的属性、英文标签、中文运营标签、类型与校验；动态表单与后端共用 |
| templates | 项目ID、数据类型、单位、方法、精度、条件、必填、复测及证据要求；工作台和完整性守卫共用 |
| comparison | 可比项目、单位换算、分组与差异规则；仅在批准比较范围使用 |
| limits/report_blocks | 能力边界、限制与双语说明；报价、报告按快照引用 |
| offers/prices | 已批准类目×服务×模板×数量/选项的可售组合及版本化计价；禁止仅凭同一 pack 放行 |

导入与后台保存都须 schema 校验，发布需独立审核和审计。配置失败只阻止该草案发布，不能因管理员保存了未完成草案导致正在运行的应用停机。CI 验证内置种子和受支持 schema 版本。已发布资源内容哈希与版本永久可查，不通过重启或文件变更覆盖正式配置。

### 3.4 下单与执行

GET /catalog 返回 ACTIVE 类目及可售 offers；表单按 offer_id 获取。报价输入 `lines[{category_id,offer_id,quantity,options,attributes}]`，输出每行不可变模板/价格快照、合计与交期。报价、正式订单行、实物、检查组与任务按§4.2/7.5关联。逐行数据结构见§4.2。

检查引擎从任务锁定模板读取类型、单位、方法、精度、复测、证据和报告区块；不得在订单/支付/报告核心写 apparel 字面量分支。测量结果状态与测量值独立，未检查和不适用必须显式表达。

### 3.5 第二类目验收

开发环境从后台配置 Bags，再配置 Home 影子模板，完整走通报价、订单、收货、检查、网页及 PDF 报告，保存通用代码零修改证据。生产未审批类目保持 PLANNED。新仪器、新测试方法或禁限品能力须另外评审，不能只换模板宣称具备检测资质。

## 4. 数据库设计（PostgreSQL 16）

### 4.1 约定

- 业务实体用 UUID，应用可生成v7；空库夹具可用数据库随机UUID，审计与 outbox 使用顺序号；复合键、时间列和不可变历史记录按 §4.2 各表定义。
- 枚举一律用 `text + CHECK`，不用 PostgreSQL ENUM 类型，便于迁移。
- 金额用整数最小货币单位；检查数值用 decimal/numeric 与模板 unit_code，范围/精度由模板定义，不把所有测量限定为厘米或正数；包裹重量仍用整数克。
- 外键默认 `ON DELETE RESTRICT`。**业务数据不物理删除**，只改状态；删除请求走脱敏流程（第 15 章）。
- 需要扩展：`citext`、`pgcrypto`。

### 4.2 空库结构基线

项目的关系模型集中保存为 [schema.sql](contracts/schema.sql)。仅用于 PostgreSQL 16 空库首建。后续增加迁移文件并核对已有数据升级，生产升级前在脱敏副本验证。此基线不写生产价格、客户或员工凭据。

| 对象 | 主记录及写入时机 | 关键约束 |
|---|---|---|
| 客户 | 注册完成服务写 users、memberships、已验证身份和 customer_receiving_profiles | 收件码唯一，绑定同组织成员。身份连接和注册事务见 §21 |
| 类目与报价 | 类目树、service_types、获批能力、template_versions、service_offers 和 offer_templates 决定每行可购范围 | 配置负责人审核后发布，服务端在报价/提交时复核，历史快照保留 |
| 委托 | orders 为订单头，每个 order_line 有自己的类目、套餐、数量与模板。录入草稿时保存逐件字段，确认价格时存 inspection_quotes | 服务费确认后按每行数量生成 expected_items。接受的报价/委托范围变更写 scope_revisions |
| 入仓 | 一包可登记多件 warehouse_items。每件按 order_line_item_links 关联已确认的委托位置 | 同一有效位置和物件最多一次匹配。samples 是受检实物视图，实物码与在库数量由 warehouse_items 管理 |
| 作业 | task 关联单件 assignment 或同一行的 group。inspection_results 按任务、项目、组件和尝试保存 | 模板版本外键、最终结果唯一、缺测原因有约束。类型、能力、单位及证据在提交事务再核对 |
| 报告 | 一个订单可有多个 report_versions。复核通过后生成私有英文PDF | 确认文件哈希才发布，已发布版本锁定，修订新增版本 |
| 寄件与钱 | 指令归实物，批次归组织，shipment_items 表达每包清单。charge_items 指向检查/发运/保管报价之一 | 付款归收费项，跨订单分摊写 charge_allocations，退款绑定实际付款。每件退回再寄起新指令 |
| 运单 | tracking_records 关联入仓预报、实收包裹或实际寄件，各段独立 | 活动运单和生成代次防串单。中文来源、英文快照、订阅与异常表见 §19 |

### 4.3 数据库与服务层职责

数据库执行显式外键、唯一索引、金额检查以及模板、已发报告和审计冻结。服务层对每条访问应用组织和角色授权。同一事务按组织→报价/收费→批次→物件ID排序锁定相关记录，然后检查版本、允许状态、所有权、能力、实物位置、费用和授权，提交业务变更、审计和outbox。多个实体跨组织同时查询时逐个执行权限校验。唯一索引冲突转可恢复业务错误。作废、撤销、退回和重新分配均保留历史。

### 4.4 可复现核对

在空测试库依次运行 `psql -v ON_ERROR_STOP=1 -f docs/contracts/schema.sql` 和 `psql -v ON_ERROR_STOP=1 -f docs/contracts/verify.sql`。测试事务最后回滚。使用两类目各15件、物件先入库后建委托，覆盖跨租户、重复绑定、已发布模板改写、未说明缺测与无PDF发布等失败场景。应用授权、真实服务回调和并发事务由对应实施任务测试。

## 5. 状态机与转移规则

### 5.0 数据与计时

**对象归属。** 用户注册得到的是个人收货标识，所有用户可以共用同一个仓库物理地址。地址/客户码不代表订单号或实物标签。用于数量为 N 的订单，同款可批量建档，系统展开 N 个委托位置；逐件检验与处置始终指向具体实物。

**注册、购买与到仓顺序。** 首次注册即签发账户码，同一客户终身复用；默认地址是后台共用仓址，收件人显示“仓库收件人 + 客户专属码”。管理员可录入多个地址，事务内切换唯一默认，保留旧地址版本与在途预报快照；上线须有有效默认地址。账户码不依赖开单或支付。用户从账户复制地址到商家结账页，商家发货后登记承运商和原始运单，可关联本人的质检草稿、已付单，或先保存为待选单。未登录不能查询码或他人归属。

扫码和手工搜索共用 lookup：先按规范化运单查预报和实收包裹，再显示客户码、已绑定订单及逐件明细。仅定位到用户时展示该用户待关联订单；重复或冲突时要求核实，禁止猜单或覆盖其他客户归属。预报、绑定与认领在服务端锁定记录并核对个人组织归属。未付款的来件照常入仓、贴包裹码和记实际数量，进待关联/待付队列；完成付款后按唯一实物编号逐件映射，无需重复收货。已核对到齐且服务已付才进入检查队列。


暂停区间取首个阻塞开启到最后一个解除。首个阻塞保存原状态和 held_at，新增阻塞不覆盖原值。已有 SLA 时按实际暂停时长顺延；到齐前的暂停不累计。争议同时使用 order_blocks 独立禁止出库，即使服务已取消或已关闭。

### 5.1 实现规范

- 每个状态机在 `packages/core/state/` 里用**表驱动**定义：`{ from, event, guard, to, effects }`，不允许散落的 `if`。
- 对外只暴露 `transition(entity, event, actor, ctx)`。内部在**一个数据库事务**里：`SELECT ... FOR UPDATE` 锁行 → 校验当前状态与守卫 → 更新状态 → 执行副作用（写审计、写 outbox、更新关联表）→ 提交。
- 非法转移抛 `ILLEGAL_TRANSITION`（HTTP 409），守卫不满足抛具体错误码（见 7.2）。
- 副作用里**不直接发邮件**，只写 `outbox_events`，由 worker 消费后写 `notifications` 并发送。
- 每个转移必须有单元测试：合法路径一条、每个守卫的失败路径一条。

### 5.6 客户逐件处置（R1）

每件授权独立，合包/拆包发运与报价以 §20.1 为准。旧单件操作必须转为单件发运批次，禁止在批次之外另建费用和交接路径。

普通寄件或退卖家依次经过 requested → quoted → paid → approved → packed → shipped → completed。报价接受记录与支付确认分开；实际交接写入运单、员工、照片和时间。completed 表示仓库交接证据已核对。快递显示退回时创建待收回任务。实际收到的每件才恢复库存、开放新指令并通知客户。商家签收与快递退回保留在物流轨迹。超管冻结、未结争议、缺付款或扫描不符均禁止交接。

续存使用 retain，同样先授权报价与付款；到账后原子写 storage_until、关闭指令并发送收据，不创建运单。普通续存不建立参考样。客户在交接前可撤销；若已付款，先阻止继续拣货，按原收费项进入退款审批。每件最多一个活动指令。R1每件指令对应一件样品；寄件按§20.1归入发运批次，共享已确认的逐包报价，不能按件重复收同一包运费。续存仍按件期限计费。

换样保留旧实物、标签与证据，结束旧物件与委托位置的绑定并记录原因，实际收到新件后以其自身码建立新绑定。已取消的位置保存 in_scope=false。对比组在组内使用A/B/C标签。三改二仅在未到齐、未开检且拟剔除样品未到时允许；事务保存变更前后 SKU、差额和剔除标签，沿用原报价时点的两件价，原付款快照不可修改。剔除件后到时隔离核实并联系订单内待办；到齐计数仅检查 in_scope 样品。

### 6.3 数据访问规则

1. **客户只能读写所属组织的数据**；访问他人订单、样品、媒体一律返回 404（不泄露存在性）。
2. **员工端隐藏支付信息**：收货员、检查员、复核员看不到客户邮箱、付款金额；需要联系客户的事项走客服。
3. **媒体访问**：客户拿到的是 10 分钟有效的签名 URL；员工端同理；媒体接口先校验订单归属再签名。
4. **报告分享链接**（R1基础只读）：令牌仅存哈希；匿名访问只返回报告快照里的字段，不返回订单号之外的客户信息。
5. **同一人制作与复核**：生产发布须独立人员复核，制作人包括该版本涉及的检查任务执行人。
6. **敏感操作要求二次验证**：改价、批准退款、改角色，均要求员工本次会话已完成 MFA。

## 7. API 规格（REST，JSON）

交易端点以 §7.5 为准，通用模板后台在 /staff/admin/templates 创建、预览和提交草稿，独立复核后发布。其他端点按下表及 §§19–22 的权限与输入字段实现。

### 7.1 通用约定

- 前缀 `/api/v1`；员工接口前缀 `/api/v1/staff`，仅员工会话可访问。
- 认证：`HttpOnly`、`Secure`、`SameSite=Lax`会话cookie；普通会话写请求使用会话绑定CSRF token并核对Origin；OIDC/Webhook例外边界见§21.4。
- 请求与响应全部用 Zod 校验；时间字段 ISO 8601 UTC；金额字段 `*_cents` 整数。
- **幂等**：下列接口必须带 `Idempotency-Key` 请求头（UUID）：`POST /orders/{id}/submit`、`POST /staff/intake/check-in`、`POST /staff/orders/{id}/refunds`。同一键同一请求体返回首次响应；同一键不同请求体返回 422 `IDEMPOTENCY_KEY_REUSED`。
- **分页**：游标分页 `?cursor=&limit=`，`limit` 默认 20、最大 100。
- **限速**：见 7.4。
- **错误格式**：`{ "error": { "code": "STRING", "message": "...", "details": {} } }`。

|---|---|

### 7.5 交易请求与响应

交易主线使用 [core.openapi.yaml](contracts/core.openapi.yaml)，基础地址 /api/v1。文件给出请求、响应、角色、幂等键及错误返回。客户/员工其他页面读取与管理命令见 §7.3、§19.7、§20.1、§21.6 及 §22。客户端在版本冲突后重新读取资源，由用户重新确认影响金额、授权或清单的变更。

草稿以 `lines[]` 提交；服装标准质检数量30和同类对比数量3是两个独立订单行。POST /orders/{id}/quotes 计算逐行报价、收费总额、锁价期限和交期。submit 接受该 quote_id 与条款，返回收费项。客户端再调用 /charges/{id}/checkout 跳转 Stripe。重放返回原结果，处理中的支付返回处理中状态，报价过期或被替换时提示重新确认。

### 8.3 运动套装模板 `templates/sports_set.v1.json`

套装采用 §8.7 的服装复测策略。套装的每个样品包含**两个组件**（`top`、`bottom`），按 `attributes.top_type`、`attributes.bottom_type` 动态选择测量点与检查项。

## 9. 报告规格

### 9.1 装配流程

`assembleReport(orderId)`（在 `packages/core/report/`）：

1. 读取各订单行、有效委托位置、实际物件、对应任务的模板与最终结果、已就绪证据，再计算覆盖数量。
2. 标准质检按委托总数、已检数、异常数和逐件记录装配，按编号查看证据，不要求并排比较；只有 compare 才按 `comparison.json` 的 sections 生成对比区块；固定声明块从 `limits.json` 与 `report_blocks.json` 引用。
3. 输出**自包含的快照 JSON**（9.2），写入 `report_versions.snapshot`。快照里只存媒体 ID，不存签名 URL。
4. 快照一经发布不可变；客户端渲染只读快照，不再回查测量表，保证历史版本可重现。

所有报告均含行级 sections[]，每段保存 order_line_id、service_type、template_version_id、expected_count、checked_count、task_ids、执行方法和证据引用。§9.2仅为一个对比段的展示示例。

### 9.3 完整性检查（`checkCompleteness(taskId)`）

返回 `{ ok: boolean, missing: [{ sample_id, kind, code, hint }] }`，`kind` 取 `measurement`、`photo`、`observation`、`order_photo`。通过条件（缺任一项即 `ok=false`）：

| 规则 | 检查内容 |
| --- | --- |
| M1 | 模板中 `required=true` 且适用的每个测量点，每件样品都有一条 `is_final=true` 的记录（有值，或写了 `reason`） |
| M2 | 按模板的测量策略校验次数和复测；一次测量的项目无需复测。服装使用 §8.7；无法测量的点按 M1 填原因 |
| M3 | 可测且需证据的点必须有当前任务、物件、component 与 point_code 一致的 ready 照片；无法测量记录原因与现场说明照 |
| M4 | 每个适用必拍项须在当前会话、样品、组件及 shot_code 下有 ready 照片；订单级项独立匹配 |
| O1 | 每个适用的观察项都有状态；不能为空，也不能全部留 `NOT_TESTED` 而没有原因备注 |
| O2 | 状态为 `OBSERVED_ISSUE` 的项必须有 `severity`、`part_code`、`note` 与至少一张照片 |
| O3 | 不适用的项目必须被系统自动标为 `NOT_APPLICABLE`（检查员不手动处理） |
| P1 | compare 订单按锁定包 comparison.json 的 order_shots.codes 核对 ready 证据；未声明的镜头不要求。服装清单见 §8.4 |
| U1 | 所录单位须等于模板对应测量点的 unit；仅比较同一项目、组件和单位 |
| S1 | 样品标签、编号在照片上可识别（人工复核项，系统仅检查照片数量） |

### 9.4 措辞校验

文本字段（观察备注、客户可见说明、复核备注）在提交时做校验：命中禁用模式则 `FORBIDDEN_WORDING`。默认配置 `forbidden_terms`（不区分大小写，可在后台追加，不可删除内置项）：

```
Certified | Certificate | Lab Tested | Laboratory | 100% | Defect[- ]?Free | AQL | Authentic | Genuine | Counterfeit | Fake |
Guaranteed | Safe for | Non-toxic | Hypoallergenic | Passed | Failed | Approved | Rejected | Best | Worst | Recommend |
ΔE | Delta[- ]?E | Spectrophotometer | Opaque | Squat[- ]?proof
```

- `Passed`、`Failed`、`Approved`、`Rejected` 仅在 `tolerance` 存在且该测量点有公差时，由**系统自动生成**的字段允许出现，人工文本一律拦截（替代词：`Within stated tolerance`、`Outside stated tolerance`）。
- 品类包 `limits.json` 的 `extra_forbidden_patterns` 追加到同一校验。
- 推荐用词：`Observed`、`Measured`、`Not inspected`、`Reference differs`、`Within stated tolerance`、`Outside stated tolerance`。

### 9.5 复核清单（批准时必须逐项勾选）

1. 每件样品的编号与照片上的标签一致，没有串样。
2. 按模板复核计量证据，有测量项目时抽查至少3项或全部项目（不足3项时）；纯目视模板复核其必需观察与照片，不强制制造测量值。
3. 模板包含目视色差时，仅描述可见差异/未见明显差异/无法判断，不向未检查类目强加该章节。
4. 没有对整批或工厂的结论；没有认证性措辞。
5. 照片中没有泄露其他客户信息、地址、供应商联系方式。
6. 缺陷描述有位置与图片，严重度与例图一致。

### 9.6 发布与访问

- 发布即对订单所属组织可见；通知走 outbox。
- 图片展示用缩略图（长边 800 px）与原图（点击放大），均为签名 URL。
- 报告页水印（R1 PDF；图片导出按后续范围）：只含 `QC Warehouse` 与报告编号，不含客户公司、邮箱、供应商。
- 分享链接（R1基础只读）：32 字节随机令牌，只存哈希；有效期 1、7、30 天可选；可随时撤销；匿名访问只读快照，不返回订单号以外的客户信息，并加 `noindex`。
- PDF（R1）：由服务端渲染报告页，文件名 `QCW-{report_no}-v{version}.pdf`，每页页脚显示报告编号与页码、“Findings apply only to the samples received.”

PDF 与在线报告从同一不可变候选快照生成，记录文件 checksum、语言、渲染版本和生成状态。审批后先生成私有 PDF 并校验，再事务提交发布及 outbox；生成失败保持待发布，队列可重试，不发送“报告已就绪”。下载校验组织权限，链接短期签名，修订生成新文件。动态中文观察、未检查原因及方法说明保留原文，必须提供经复核的英文内容才能对客户发布。详见 T81/T82。

### 9.7 工作日与 SLA 计算

- `addBusinessDays(start, n)`：按 `Asia/Shanghai` 时区，周一至周五为工作日，`app_config.calendar.holidays`（日期数组）与 `calendar.extra_workdays`（调休上班日）覆盖默认。
- 起点是 `samples_ready_at`，使用已确认报价的数量档/模板工时/产能交期；`on_hold` 按实际阻断任务记录暂停原因，恢复后按政策顺延。平台原因延误不自动扩大已对客承诺，须通知和处理。
- 超过 `sla_due_at` 仍未发布报告的订单进入后台“超时”列表，并每天一次提醒管理员（不通知客户，除非人工处理）。

## 10. 费用、退款与成本规则

### 10.1 价格计算

各行按锁定价格规则计算。按件行取数量档单价×数量，对比行取套餐价，附加项按报价明细累加。每行存模板、数量档、选项、币种、金额与交期，订单汇总为inspection_quotes。无适用规则返回人工报价待办，正式环境只使用已审批规则。

### 10.2 附加费用与国内运价

合包按实际包裹计费，批次确认和改址守卫见 §20.1。人民币快递成本与USD对客报价分别记录，物流查询 API 不提供本平台的最终运费报价。

| 项目 | `[DEFAULT]` 规则 | 说明 |
| --- | --- | --- |
| 超期保管费 | 免费保管期 30 天（自报告发布起），之后每件每 30 天 $3 | 配置 `storage.free_days`、`storage.overdue_fee_cents_per_30d` |
| 重新打包 | 每次 $2 | 仅当客户要求改包装或二次寄出 |
| 国内寄件 | 快递实际费用 + 处理费 $2 | 先报价后付款，不事后扣费 |
| 超出标准的检查需求 | 不进标准套餐，走询价工单 | 避免变成定制服务 |
按仓库称重（克）和目的地选择已生效的 USD 运价版本。每档定义 region、首重克数及费用、续重克数及每档费用、处理费。总额 = 首重费 + ceil(max(0, 重量−首重)/续重克数) × 续重费 + 处理费。规则发布前拒绝区间重叠、续重单位为零或金额为负。无法命中时仓管在系统内说明原因并报价，客户线上确认。快递实付另记成本。R1 默认报价有效 48 小时；地址、重量或费用改变须产生新版本。续存每件每 30 天计价，延长起点为原到期日；逾期时明示欠费与新期限，在客户确认前不得自动扣款。

客户先自行向商家申请退货，在 return_to_seller 指令中确认已办理并填写商家指定的退货地址、收件人及必要联系方式。国内退货运费由客户承担，沿用报价、确认及支付流程。仓库按授权地址代寄，在交接时登记实际承运商及寄回运单号，随后在客户订单展示并通知。客户提交时无需提供商家申请编号或快递单号。原始入仓运单与实际寄回运单分开保存。

### 10.3 退款规则（`[DEFAULT]`，由超级管理员可按个案调整并写原因）

| 订单所处阶段 | 退款比例（服务费） | 备注 |
| --- | --- | --- |
| 已付款，无任何样品入仓 | 100% | 支付渠道手续费由平台承担 |
| 部分或全部样品已入仓，尚未开始检查 | 检查费 100%；寄回费用按独立收费项目核对，已另付的运费不得再扣 | 样品转入处置流程 |
| 检查已开始，报告未发布 | 50% | 已投入人工；若是平台原因（丢件、错检）则 100% |
| 报告已发布 | 0% | 如因平台差错（测量或事实错误）经复核属实：免费重检或 100% 退款，二选一，由客户选择 |
| 三件改两件对比 | 退价差（三件价减两件价） | 一次性，订单仅可操作一次 |
| 超出范围订单（样品属禁限品等） | 100% | 货物按禁限品流程处置 |

退款流程：客户自助申请或 support 代录（填原因）→ super\_admin 批准（需 MFA）→ 系统调用支付渠道退款 → 回调确认 → 记录 `refunds`。**任何退款都不自动解除保管或寄件责任**，样品仍需走处置流程。

### 10.4 单笔贡献计算（后台财务视图）

```
贡献 = 实收服务费
     − 支付手续费（来自支付渠道结算数据，写入 order_costs.payment_fee_cents）
     − 直接人工成本（Σ step_timings.seconds / 3600 × labor.hourly_cost_cents）
     − 耗材（order_costs.materials_cents，按配置的每件耗材标准自动计入）
     − 退款金额
     − 获客成本（渠道佣金 + 广告费分摊，写入 order_costs.acquisition_cents）
```

- `labor.hourly_cost_cents` `[DEFAULT]` 700（即 $7/小时，仅为占位，**必须按家人实际工时和合理机会成本改**）。
- `materials.per_sample_cents` `[DEFAULT]` 50。
- 国内寄件与国际运费的代收代付**单独记录**，不进入服务收入，也不计入毛利。
- 后台财务视图必须能按日期、渠道、SKU、品类筛选，并导出 CSV；`is_test` 订单不计入。

### 10.5 税务与发票

`[DECIDE]` 取决于经营主体与目标市场。系统先提供**收据**（订单号、金额、日期、服务内容、收款方名称），发票与税号字段在 R2 预留；价格展示为含税还是不含税，按主体与支付渠道的要求确定。

### 10.6 收款、对账与适配器

内部接口 createCheckout(charge, attempt)、verifyWebhook(rawBody, headers)、fetchStatus(ref)、refund(payment, refund) 由 StripeProvider 实现。检查、寄件及续存收费统一走 Stripe Checkout；退款审批后通过 Stripe 原路退回。开发和预发布使用 Stripe 测试模式。生产收款门槛见 C.10；未开放时保留订单并提示暂不可支付，服务端拒绝创建真实 Checkout Session。

每笔收费可有多次尝试。成功时锁 charge_items，以 applied_payment_id 判明是否首次履约。已应用另一笔付款时记录实际多收、冻结重复履约并生成待退款工单。旧报价或已作废收费的迟到款同样进入核对。支付、应用收费效果、审计及 outbox 同一事务。批准退款时锁支付记录，以实收减已成功退款及已批准在途金额确定可退余额；失败释放预留，渠道后台退款以独立 refund 对象 ID 去重。

1. **逐件任务**：标准质检展示数量、已检/待检/异常数和实物编号，可扫码定位、搜索分页、继续未完成件。对比单另提供 A/B/C 快捷切换。每件独立保存数据、证据和进度。
2. **步骤计时**：进入步骤自动 `steps start`，离开自动 `end`；有“暂停”按钮（午休、接电话），暂停期间不计时；页面失焦超过 5 分钟自动暂停并提示。
3. **①准备**：确认样品标签贴在台面、尺与秤已校验（勾选并记录日期）。
4. **②拍照**：按模板 `shots` 逐项拍摄，每项显示参考示例图；拍完自动入队上传，缩略图显示上传状态；缺必拍项时步骤圆点为红。
5. **③测量**：根据当前点的测量次数、单位、示意图和阈值录入；按模板要求绑定证据，无法测量需填原因。服装复测见 §8.7。
6. **④观察**：按模板列出可用结果状态；选“有问题”弹层要求选严重度、部位、写说明、至少一张照片；不适用项自动灰显。
7. **⑤对比照**：compare 按锁定包的订单级镜头清单操作，显示实际样品标签和拍摄指引；无此项时跳过。
8. **⑥提交**：展示完整性检查结果（调用 `/completeness`），缺项可一键跳转；通过后“提交审核”，并完成文字校验（禁用词命中则高亮）。
9. **离线与恢复**：IndexedDB 按员工与会话隔离，携带 revision 提交批次，服务端锁 task 校验并递增；冲突保留两版供员工比较，已提交会话拒绝旧写入。
10. **防误操作**：提交、批准、hold 等关键按钮二次确认；已批准的数据不可再改，只能走修订。

#### 高保真原型交付与走查顺序

D11–20 采用 30 件标准质检主例单，并另备三件对比及套装例单，原型使用固定数据、可点击分支和真机尺寸。原型验收后再进入业务编码。

| 编号 | 操作路径 | 必须能验证的分支 |
|---|---|---|
| U1 | 注册领码和地址→商家购物→登记运单→30 件质检→条款→付款→查订单 | 价格改变、会话过期原单重付 |
| U2 | 待办深链→实物不符→比较证据→回应 | 接受、替换、寄回；三改二展示差额 |
| U3 | 扫码→隔离或收货→贴标→作业→断网恢复→提交 | 故意漏下装证据，点缺项回到对应组件 |
| U4 | 复核退回→修改→批准→客户报告→证据→版本历史 | 旧版只读、能找到数值对应刻度照 |
| U5 | A 集运、B 退卖家、C 续存→报价→支付→交接→查询 | B 缺资料，A、C 各自继续 |
| U6 | 后台工单→原收费→退款申请→MFA 审批→结果 | 资金记录和实物库存分别可查 |

## 12. 通知与邮件

### 12.1 规则

- 所有邮件由 worker 从 `outbox_events` 生成，写入 `notifications` 后发送；同一 `dedupe_key` 只发一次。去重键包括模板、对象 ID 和业务发生标识（报价版本、退款 ID、报告版本或提醒轮次），同一轮重试沿用原键。
- 邮件为英文纯文本加简单 HTML；**不含营销内容**；每封只有一个主要操作入口；页脚含客服邮箱。
- `is_test` 订单的邮件一律发往 `TEST_INBOX_EMAIL`，主题前加 `[TEST]`。
- 发送请求与真实投递分离；临时失败可退避重试，超时结果未知先核对，硬退信/投诉抑制重发，详见§22.2。邮件服务故障时仍通过后台和独立监控通道告警。
- 所有邮件深链指向 APP_URL 下经授权可见的账户、物件、发运、收费或订单详情，**不在邮件里放图片或报告内容**。

## 13. 后台任务（pg-boss）

物流任务 `tracking.subscribe/process_inbox/reconcile/query/translate_review/alert_watch` 的触发、冷却与失败恢复见 §19.5–19.8；查询重试不能直接沿用普通任务的分钟级退避绕过限频。PDF任务 `reports.render_pdf` 见 §9.6。

| 任务 | 频率 | 行为 |
| --- | --- | --- |
| `outbox.dispatch` | 持续 | 消费 `outbox_events`，生成 `notifications` 与后续任务 |

## 19. 全程物流查询与中英文展示（R1 必须交付）

### 19.1 业务范围与责任

注册领码 → 客户在商家购物 → 在 PAGE-C07 登记商家实际发货运单 → 系统自动跟踪 → 仓库扫描/搜索并实际验收入库 → 检查与报告 → 客户授权集运/国内转寄/退商家并支付报价 → 仓库打包、填写实际寄出运单并交接 → 系统持续跟踪至签收或异常处理结束。

每一段独立建档：`inbound` 商家到 QCW；`outbound_forward` QCW 到集运仓；`outbound_domestic` QCW 到国内地址；`outbound_return` QCW 到商家；`carrier_return` 承运商退回 QCW。同一商品可有多段，禁止用退货运单覆盖原始入仓运单。客户自行向商家申请退货并提供地址、自付运费，仓库寄出后回填运单。商家是否退款由客户与商家处理，物流签收不触发原购物退款或 Stripe 退款。

R1 包含站内轨迹、自动更新、异常待办、英文客户页面、中文后台与查询 API。预约取件、购买面单、自动打单、承运商拦截改址和国际段跟踪不属于此接口范围。交到集运仓后，显示国内段签收，不能据此显示“已送达你的海外地址”。原有 FEAT-D07 的后置范围仅指寄件下单/面单接口。

### 19.2 默认供应商与接入契约

`[DEFAULT]` 首期使用 **快递100企业 API**，封装 `Kuaidi100TrackingProvider`。这是开发默认选型，尚未开户、购买额度或完成真实运单联调。官方查询支持 `lang=zh/en`；采用中文订阅推送和英文查询快照。相关接口与约束核对日期为 2026-11-04，依据[实时查询文档](https://api.kuaidi100.com/document/5f0ffb5ebc8da837cbd8aefc)和[订阅推送文档](https://api.kuaidi100.com/document/5f0ffa8f2977d50a94e1023c)。供应商参数仅出现在适配器，不进入订单状态机。

| 能力 | 服务端调用约定 |
|---|---|
| 订阅 | POST `https://poll.kuaidi100.com/poll`，表单 `schema=json`、`param`；param 含 company、number、key，以及 parameters 下的 callbackurl、非空随机 salt、resultv2=4、必要的 phone |
| 查询 | POST `https://poll.kuaidi100.com/poll/query.do`，表单 customer、param、sign；param 含 com、num、lang、resultv2=4、必要的 phone。sign 为 `MD5(param原字符串 + key + customer)` 的大写十六进制 |

| 回调接收 | 验真且持久化 inbox 后返回 `{result:true,returnCode:"200",message:"成功"}`；重复合法消息同样确认。数据库失败不得确认成功；业务处理异步、可重放 |

适配器内部接口：`subscribe(tracker, subscription)`、`query(tracker, locale)`、`verifyCallback(rawForm, subscription)`、`normalize(snapshot)`。返回明确的 `ok/no_record/needs_verification/unsupported/retryable_error/auth_error/rate_limited`，不得把所有失败转换为“运输中”。生产必须验证 HTTPS 回调可用；官方文档提示需联系供应商开通 HTTPS 兼容，未验证前不能上线该链路。

配置 `TRACKING_PROVIDER=kuaidi100`、`KUAIDI100_KEY`、`KUAIDI100_CUSTOMER`、`TRACKING_CALLBACK_BASE_URL`、密钥管理中的凭证版本与 salt 加密密钥。测试与生产独立账号/额度或供应商确认的隔离方式；密钥不可写入前端、日志、种子或后台可读明文。超管只看是否配置、最近校验时间、到期/额度告警，可触发健康检查，不能通过页面任意指定外部查询 URL。

### 19.3 承运商识别、电话验证与单号纠错

1. `carriers` 维护稳定内部 code、供应商 code、中英文名、可用性、单号格式、是否需要电话及所需形式。初始验收清单覆盖顺丰、中通、圆通、申通、韵达、极兔、京东、邮政/EMS，逐家记录实际支持，未验证的不可宣称已覆盖。规则和权限以供应商当前账号为准。
2. 客户输入单号可提示候选承运商，存在歧义必须选择。无确定承运商仍允许保存预报，状态 `needs_carrier`，不盲目订阅多个公司或向客户展示他人轨迹。识别结果不是归属证据。
3. 单号去首尾及扫描器附加空白、拉丁字母大写，保留前导零和承运商认可的连字符；绝不转数字。长度与字符按承运商配置校验。买家填写的是快递运单，不是淘宝订单号。
4. 电话校验使用这票快递实际下单的收/寄件电话。入仓优先预报锁定仓址电话，退货/转寄使用实际面单电话；虚拟号码按该承运商规则提交。缺失或失败显示 `Verification needed`，不能让客户反复填自己的海外手机。必要字段加密保存、按角色脱敏，更新有审计。
5. 未收货的预报可由客户更正，服务端递增 revision，旧 tracker 标为 superseded，新 tracker 与预报绑定，同事务 outbox。已入库的原单号仅仓管核验凭证后修订。已交接出库的错单号须仓管录原因、面单证据并复核后发布修订，不能修改交接事实。
6. 供应商更正承运商、转投、换单号只形成候选关联，禁止自动改租户、订单、地址或授权。旧单回调只归旧 tracker。单号可能被承运商复用，系统以运输实例而非永恒单号唯一；同号再次使用需核对发货日期与实物，新增实例，历史租户数据不相互展示。活动实例跨客户冲突进入私密认领工单。

### 19.4 数据模型与约束

本节定义物流行为，数据库字段、索引和关系见§4.2的空库基线。所有表使用 UUID 主键、UTC 时间、外键 RESTRICT，以下业务键不得放入无约束 JSON。

| 表 | 必要字段与约束 |
|---|---|
| carriers | code UNIQUE、provider_code、name_en/name_zh、phone_rule、tracking_pattern、enabled、verified_at；供应商映射按 provider 唯一 |
| tracking_records | org_id 可空（未认领件仅员工可见）、direction、advice_id/package_id/shipment_id、carrier_code、tracking_norm、generation、supersedes_id、source_phone_ciphertext、transport_state、sync_state、latest_event_at、last_success_at、next_query_at、closed_at、revision；至少一个业务关联，关联对象组织须一致 |
| tracking_subscriptions | tracker_id、provider、callback_token UNIQUE（随机至少32字节）、salt_ciphertext、credential_version、status、attempt_count、last_error_code、next_retry_at；每 tracker/provider 最多一个活动订阅；技术重试复用 token/salt，不重复创建 |
| tracking_inbox | subscription_id、payload_sha256、received_at、encrypted_payload、verified_at、processed_at、attempt_count、error_code；UNIQUE(subscription_id,payload_sha256)，原始正文不进应用日志 |
| tracking_snapshots | tracker_id、source、locale、payload_hash、fetched_at、latest_event_at、provider_state、events_json、schema_version；UNIQUE(tracker_id,source,locale,payload_hash)，快照不可变，中英文分别保存 |
| tracking_events | tracker_id、fingerprint、source_time、occurred_at、source_timezone、status_code、location_code、text_zh、source_snapshot_id；无供应商事件 ID 时 fingerprint 用时间原值+状态+位置+原文的哈希；不能仅按时间去重 |
| tracking_translations | event_id、source_hash、locale、text、source(provider/manual_reviewed)、reviewer_id、reviewed_at；UNIQUE(event_id,source_hash,locale)，原文变更旧翻译不沿用 |
| tracking_alerts | tracker_id、kind、episode、state(open/acknowledged/resolved)、assignee_id、due_at、ticket_id、last_notified_at；UNIQUE(tracker_id,kind,episode)，重新发生可建下一轮 |
| tracking_query_attempts | provider、carrier、tracking_norm、requested_locale、reserved_at、completed_at、outcome；跨客户/语言/任务共享频控账本，不提供客户跨租户读取 |

运单归属不能由物流事件决定。tracking_records 上 advice/package/shipment 可以随入仓补齐，但只指向同一运输实例；已认领组织更正走授权审计并撤销旧访问。活动运单去重用 `(provider,carrier_code,tracking_norm)` 的运输实例锁处理，历史实例保留。回调 token 绑定唯一实例，不能按运单号查到“最新用户”后直接写入。tracking_records.parent_tracker_id为可空自引用，禁止形成环，不作为库存或所有权继承依据。

供应商同时返回多票、子母单时，各实际运单单独建 tracker，`parent_tracker_id` 仅表达物流关系；仅母单签收不能把所有子单和商品标为签收。无子单数据显示覆盖不完整，由工作人员核实。

### 19.5 状态与自动更新

运输状态：`information_received / picked_up / in_transit / out_for_delivery / delivered / exception / returning / returned / cancelled / unknown`。同步状态另存：`pending / active / no_record / needs_carrier / needs_verification / unsupported / delayed / provider_error / stopped / superseded`。中文/英文标签由稳定 code 的字典生成。映射表以供应商版本化 fixture 验证，未知代码落 unknown 并告警，不能凭数字大小推断状态顺序。

物流签收只增加承运商事实。入仓仍需收货员扫描、照片、数量核对和样品映射；快递签收但未入库显示 `Delivered by carrier · Warehouse check-in pending`。出库“已交接”和“已签收”分别显示；运输退回只创建待收回任务，实际重新入库必须扫码、清点及留证。检查订单关闭后，未结束的发运和物流异常继续跟踪。

有效回调先落 inbox → worker 校验 tracker/generation、运单和承运商 → 保存快照与去重事件 → 更新运输投影与待办 → outbox 通知。全量重推、乱序、重复都可重放。迟到的旧在途事件不能覆盖较新的签收；同时间冲突保留来源并标记待核对。若较新的权威快照修正签收或进入退回，保存修订和异常，不能把签收当不可逆终态吞掉后续信息。没有时间依据的冲突由客服核对。

`[DEFAULT]` 中文推送为主；新增记录先排英文查询，推送停滞时补中文查询。查询所有语言合计同一承运商/单号至少间隔 60 分钟、滚动24小时最多24次，所有手动刷新与重试共同使用数据库锁和额度预算。该内部上限严于官方查询限频，供应商限制变更只可收紧或经重新验证调整，不能刷新页面直接调用收费接口。页面每60秒读取本站缓存，可即时重新读取缓存。

`tracking.subscribe` 由 outbox 触发；可重试网络故障按1/5/30分钟退避，最多3次，不把鉴权/格式错误当网络重试。超时结果未知先核对，重复订阅返回须核验本地原订阅身份，不能无限创建。`abort` 记录停止原因并确认接收，生成待办；重新订阅须核对供应商当期重复订阅限制，经冷却与预算守卫执行。`tracking.reconcile` 每小时检查失联、未处理 inbox 与应查询记录；`tracking.process_inbox` 可安全重放。

查询出现限流、余额不足、权限失效启用供应商级熔断与后台告警，保留最后成功快照及时间。无轨迹不等于未发货，供应商错误不等于包裹丢失。默认连续72小时无物流事件进入停滞待办；快递已签收24小时仍无仓库验收进入收货核对，阈值可按运营日历调整。异常一出现即提醒，无须等待72小时。

签收后保持7天低频复核（每天最多一次，期间中英文交替，推送仍接受），之后停止主动查询；存在未关闭异常、退回或客户申诉的继续按配置跟进。长时间运输由后台判断是否延长监控，不静默删除历史或自动退款。

### 19.6 英文客户轨迹与中文后台

- 后台默认中文原始轨迹，显示来源、事件发生时间、最近同步时间、同步错误与负责人。可切换英文快照便于客服核对。
- 客户默认英文状态与英文完整轨迹，使用供应商 `lang=en` 的独立快照，不只翻译状态标题。中英文更新时间分别记录，英文暂落后时明确显示 `English details are being updated` 和最新英文更新时间；最新运输状态仍按同一 code 翻译。
- 英文快照独立渲染，不能把两次查询的数组按下标或仅时间强行配对。只有事件身份、时间、状态与位置能够唯一对应时，才允许建立事件级翻译关联；否则保持整份英文快照。人工补译绑定中文事件及 source_hash，必须复核、标来源，不能覆盖原始中文证据。
- 英文接口无记录、返回中文或关键异常没有英文时，显示英文待更新说明、已知英文状态及联系客服入口，建待办人工补充。不得用未经确认的自动总结编造路线、承诺到达时间或隐藏异常。常见状态可用确定性词典翻译，完整事件仍需供应商英文或人工复核。
- 客户可显式展开脱敏原文；收件人/快递员电话、完整住址、取件码不混入默认轨迹。英文地名优先供应商英文/拼音，没有可靠映射显示可确认地区及待补充。日期转为用户时区并标明；后台中国时间。无时区的中国国内轨迹按 Asia/Shanghai 解析，原时间字符串保留，解析失败不伪造时间。
- 区分事件时间、抓取时间、仓库操作时间。估计到达时间仅在来源支持时显示且标为估计，不能根据内部 SLA 编造物流 ETA。

沿用 §7 的本站 API 前缀 `/api/v1`，下表路径省略前缀。权限在服务端根据关联资源核对；未授权对象统一404。所有返回使用白名单 DTO，不直接透传供应商全文。

| GET /shipments/{id}/tracking?locale=en | 归属本人且已授权发运；返回该包裹内商品 ID、方向、交接与运输分离的状态 |

客户 PAGE-C07 列表按包裹展示英文承运商、单号复制、运输/入库两个徽标、最新事件和待处理提示；点击侧栏或独立详情 PAGE-C17，手机用整页。PAGE-C12 发运详情复用同一轨迹组件，顶部明确 Return to seller / To your forwarder / Domestic delivery、所含商品、收件地址快照、付款及仓库交接时间。客户地址只向本组织授权者显示。

仓库 PAGE-H05/H13 显示中文轨迹与扫码实收/交接操作，两者独立；后台新增 PAGE-M16 物流监控、PAGE-M17 物流接入设置。轨迹 UI 必须覆盖加载、无记录、需验证、不支持、陈旧缓存、英文待更新、供应商故障、已签收待入库、退回、错误单号修订等状态，不能只画一张成功时间线。桌面左右分栏“包裹/商品摘要 + 事件”，手机纵向时间线，颜色同时配文字和图标。

### 19.8 通知、隐私、监控和生产门禁

新增 outbox 事件 `tracking.exception_opened`、`tracking.delivered`、`tracking.verification_required`、`tracking.corrected`、`tracking.stalled`、`shipment.handed_over`，客户邮件与站内通知英文、内部待办中文。普通路由节点只更新页面，不每站发邮件；同一异常 episode 通知去重，恢复后再异常可新发。邮件链接先登录再返回本站详情，正文不含完整地址和电话。

`[DEFAULT]` 原始回调加密保留30天，脱敏轨迹按履约记录保留策略处理，法律保全冻结删除；未认领件不可对客户开放，供应商密钥/salt不随业务导出。传给供应商只包括承运商、运单和必要校验字段，不发客户报告、商品照片或商家账号。隐私清单登记供应商与目的。

后台指标包括订阅成功率、回调到达与处理延迟、失败队列年龄、英文落后数量、电话校验失败、停滞、异常待办超时、供应商调用量和费用。队列超过15分钟未处理、已排队英文更新超过2小时未处理、预算达到80%/100%分别预警/暂停非必要主动查询，不能丢弃已收到回调。供应商没有余额查询接口时显示“人工核对时间/后台链接”，禁止伪造实时余额。

上线前须保存实际账号产品权限、HTTPS回调结果、每家首发承运商的普通/验证电话/无记录/签收/异常中英文样本、限频与重复回调证据。生产最少验证商家→仓库、仓库→集运仓、仓库→商家三条实物链路。轨迹故障不能阻止员工登记真实收货/交接，但要显示查询不可用并保留重试任务。没有凭证时可做 mock 和官方调试联调，不能标为生产验收通过。

## 20. 跨模块补漏与当前交付边界

### 20.1 合包、拆包、报价与逐件授权（R1）

- 保留逐件 `disposition_requests`，增加 `dispatch_batches`（org_id、destination_snapshot、action、revision、state）、`dispatch_batch_items`（batch_id、sample_id、disposition_id）和 `shipment_items`（shipment_id、sample_id、disposition_id）。每个活动样品只进一个未终结批次，同一实物不能进两个已交接包裹。所有成员同组织且已授权、同动作、同完整地址；不同商家退货不得因相似地址自动合并。
- 客户在 PAGE-C10 勾选多件并预览批次，可同订单拆成多个去向，也可将本人不同订单的商品合包到同一个集运仓。仅客户明确确认合包清单后生效，不跨客户合包。一个批次可装多个实际包裹，每包独立重量、运单和 tracker；清单与费用可追溯。
- 出库报价增加 `dispatch_quote_versions(batch_id,revision,expires_at,snapshot,amount_cents)，snapshot含地址、物件、逐包费用及币种`，每版含每个包裹的重量/体积适用规则、运费、处理费及合计。`charge_items.dispatch_quote_id` 只关联一个已接受报价，批次总体付清才允许发运；处理费按已展示规则收取一次，不能按逐件指令暗中重复收费。报价使用 USD，人民币实际快递成本单列币种、汇率和记账日，不混作美分。
- 付款前改清单/地址使旧报价失效并重报价；付款后改动先冻结批次、作废未交接计划，核算应退/补收并取得新授权。任何旧报价迟到付款只进入对账，不放行旧清单。已交接包裹不可撤回成待打包，仅能申请人工物流处理。
- 仓库逐包扫描装箱，实际件数及 ID 必须等于该包授权清单，拍照后录单、交接。对缺货/损坏件局部暂停，其余重新确认拆分后的报价才可发出，不能用“整单完成”掩盖剩余库存。商家拒收后重新入库，新的寄件另起授权及费用流程。
- API：POST /dispatch-batches（本人已授权的 disposition_ids）、GET /dispatch-batches/{id}、POST /dispatch-batches/{id}/confirm、POST /staff/dispatch-batches/{id}/quote、POST /staff/dispatch-batches/{id}/parcels、POST /staff/shipments/{id}/handover。写命令均校验幂等/版本/归属；handover 锁定批次、收费、处置及样品，检查授权/款项/阻断后单事务写库存、交接和物流 outbox。单件走同一批次服务。POST /staff/shipments/{id}/receive-return 由仓管提交 revision、item_ids、evidence_ids、location_id 和 received_at。只处理原清单中此次实收的件，重复扫码返回已有结果。少件留待核对，只有全部确认退回才更新整包的实际退回状态。

## 21. Gmail / Outlook 注册、登录与账户生命周期（R1）

### 21.1 注册方式与支持范围

用户于本轮明确选择 **Google / Microsoft 一键注册登录，并保留邮箱验证码备用**。邮箱地址验证与供应商一键登录是两个入口，最终关联同一个平台用户。无需客户设置 QCW 密码，也不收集其 Google/Microsoft 邮箱密码。员工继续使用独立的密码+MFA入口，客户登录不能获得员工权限。

PAGE-C01 显示 `Continue with Google`、`Continue with Microsoft` 和 `Continue with email`，首次访问与再次登录共用入口。支持 Gmail、Outlook.com 及微软个人账户使用的 Hotmail/Live 地址。首发微软应用必须允许个人账户，不能只配置公司租户导致 Outlook 用户无法登录；工作/学校账户能力另行验收后开启。Google 使用真实供应商账户认证，不仅依据 email 后缀识别身份。本要求是支持指定登录方式，不额外把注册硬编码为仅允许两个邮箱后缀，不把企业域名或微软账户别名误判为假账户。

Google/Microsoft不可用时，已验证邮箱可走验证码；不存在已验证邮箱的用户必须先完成邮箱验证，不能用供应商显示名或未验证email接管已有账号。UI提供取消授权、账户切换、网络失败、重试、收不到验证码、账号受限、联系支持等状态。

### 21.2 身份唯一性与注册事务

email_otp 身份以已验证 user_emails.id 为稳定 subject，auth_identities.email_id 与 user_id 共同校验归属。工程迁移 004 在保留用户、组织及收件码的前提下回填旧邮箱身份，绑定不一致时迁移回滚。邮箱 OTP 初次注册前仅把地址作为已验证的短时登记信息。用户内码/个人组织/永久收件码以 users.id 为主，不使用 email、Google名称或Microsoft preferred_username 作主键。外部供应商email只作提示或通知候选。供应商稳定身份键的依据见[Google OIDC文档](https://developers.google.com/identity/openid-connect/openid-connect)及[Microsoft ID token说明](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference)。其中微软email可能变化或缺失，不用它自动授权或合并账户。

Google返回已验签且email_verified=true的Gmail地址可视为已验证通知邮箱；其他Google地址按实际可验证声明或本站OTP核验，不能只凭后缀信任。Microsoft返回的email仅预填，首次作为通知/OTP登录邮箱必须通过本站OTP验证；此验证只在首次设置或换绑时要求。首次身份验证成功进入短时onboarding上下文，必要时补充并验证收件邮箱，再显示平台注册条款与隐私说明；确认注册后，在同一事务建立用户/绑定身份/已验证邮箱/个人组织/membership/唯一收件码/条款记录/outbox，再设置客户会话。相同身份并发回调和重放只得到一个用户和一个收件码。首次完成注册立即展示默认仓址；没有默认地址时仍保留个人码，显示仓址待配置并禁止用空地址引导寄件，通知管理员补齐。

已有身份再次登录复用原用户；外部身份未绑定但邮箱与既有账户相同，进入“登录既有账户后连接”的流程，不能按同名email自动合并或新建覆盖。首次注册撞上已验证邮箱也进入该流程；不因供应商缺email创建一批无从联系的正式客户账户。注册/绑定失败回滚，不能留下已分配码却无主用户。

邮箱正规化仅去首尾空白、域名标准化和明确定义的大小写策略，保留原始地址用于展示。不能对所有提供商全局删除点号或 `+tag`，不能靠字符串相似合并账户；Google登录的唯一性由其subject确定。非ASCII本地部分若首期不支持须给英文格式说明，不静默改写。更换通知邮箱后历史订单地址、发运地址及收件码不变。

### 21.3 Google / Microsoft 接入与回调

服务端用维护中的OIDC实现处理 Authorization Code Flow，启用PKCE S256、state、nonce及签名/issuer/audience/有效期验证，不能只decode JWT。Google Discovery固定可信地址，Microsoft首发选择个人账户的可信Discovery，issuer依据所选账户范围验证，禁止接受客户端提交的任意issuer/JWKS URL。生产callback精确登记HTTPS地址，开发/预发布/生产隔离client id与secret。具体供应商参数由TASK-167按官方文档及所用库验证并锁版本，不把本文当手写认证库教程。

仅请求 `openid email profile`，不申请Gmail邮件读写、Microsoft Mail.Read、通讯录、日历或离线访问权限。不因纯登录长期保存access/refresh token；完成验证后仅保留必要身份引用和审计元数据。Google头像URL不由服务器任意抓取，默认使用本地首字母头像。

本站端点统一 `/api/v1/auth/{google,microsoft}/start` 与 `/api/v1/auth/{google,microsoft}/callback`。start绑定浏览器事务及允许的站内return_path，callback使用服务端兑换、验证并一次消费事务；拒绝错误state/nonce、跨provider回调、code重放、过期事务和开放重定向。用户拒绝授权返回登录页可读提示，保留原草稿，不显示内部token或供应商敏感报错。链接账号的事务必须绑定当前用户和已验证会话，不得把一次登录回调当成绑定授权。

Google/Microsoft按钮与品牌呈现、OAuth同意页、正式域名、隐私/条款URL、账户类型、实际授权取消和回调必须在TASK-167验收。依据[Google登录配置](https://developers.google.com/identity/openid-connect/openid-connect)和[Microsoft授权码流程](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)。未提供商户自有OAuth项目时只能用测试配置，不能标为正式注册可用。

### 21.4 验证码、会话与敏感操作

验证码请求返回202及不可枚举的challenge_id、resend_after（默认60秒），具体账户是否存在不在未验证响应中暴露。格式不支持可返回422；限速返回429与Retry-After，不能一边声称“永远204”一边返回手机号/账户存在结果。验证请求传challenge_id+code，绑定purpose与发起浏览器，统一错误不区分错误/过期/不存在；修改邮箱、连接身份、注册、登录的验证码不可互换。

验证码使用服务器pepper的HMAC存储以抵抗6位码离线穷举；单次消费与失败次数递增须加锁，过期/耗尽即失效。新一代验证码发出使旧一代失效，重发不能清空账户/IP时间窗内的总失败次数。出站邮件仅在worker发送时短时取得加密验证码，发送完成/过期后删除密文，日志及通知正文归档不得保留可用码。

沿用每邮箱每小时5次、每IP每小时20次初始发送额度；另有challenge冷却、总发送预算和异常速率风控。共享IP不永久封整仓或企业用户。异常触发服务端校验的挑战或临时冷却，不能仅靠前端倒计时；外部挑战服务不可用时提供正常登录/客服恢复路径，不绕过验证码验证。

会话cookie HttpOnly/Secure/SameSite=Lax，令牌仅存摘要，登录/权限变化时轮换。默认客户30天绝对有效期、员工12小时，敏感操作要求最近10分钟内完成独立重新认证。外部身份授权有效不等于本平台账号active；每次访问检查用户状态与auth_version。退出撤销服务器会话，其他设备可逐个或全部退出。

OAuth顶层回调按state/nonce处理，供应商webhook按对应鉴别机制处理，不能套用依赖浏览器CSRF token的通用写接口规则。普通会话写接口使用会话绑定的CSRF token并核对Origin，禁止只比较两个攻击者可控制的未签名值。POST退出、换绑、连接/解除身份、取消会话都受CSRF和幂等保护。

### 21.5 连接、换邮箱、恢复与停用

- **连接登录方式**：已有账户最近重新认证 → 从账户安全页启动另一个provider验证 → 后端确认未归其他用户 → 事务绑定并通知主要邮箱。只有双方控制权都验证才连接。同一邮箱出现在不同provider不自动连接，已有两个有资产账户的合并转人工双边核验，R1不自动迁移订单或库存。
- **解除登录方式**：最近重新认证，至少留下一个已验证且可用的登录方式；解除最后方式返回409 LAST_LOGIN_METHOD。撤销相关待处理认证事务，通知客户。不能解绑他人的identity_id。
- **换邮箱**：最近重新认证+旧邮箱确认+新邮箱OTP均通过后切换主要通知/验证码登录邮箱，唯一性并发约束；撤销其他会话、失效旧OTP并通知新旧邮箱。外部身份subject不变化，不把客户商品迁到新用户；无法使用旧邮箱走恢复流程。
- **账户恢复**：可用的另一已绑定provider可登录；全部方式失效时在公开恢复入口提交联系邮箱与说明，验证新邮箱并创建私密工单。单号、收件码、姓名、截图或一次付款凭据都不能单独证明所有权。客服核验既有可信渠道/多项历史证据，独立授权人员批准；证据不足不得转移所有权，可拒绝并告知补充方式，不承诺必然找回。客服独立核实确有冒用风险后，可记录原因并临时冻结换绑/出库。匿名恢复申请本身不能冻结他人账户或阻断正常收货。
- **恢复执行**：记录恢复依据、原身份、变更、批准人、通知尝试，按经确认的规则冷却后执行；用户侧可查恢复状态。批准后撤销旧会话/挑战/恢复请求，绑定已验证新身份，原收件码/订单/实物不变。默认恢复冷却24小时，紧急例外需双人审批且留证。
- **受限/关闭账户**：restricted可查看本人履约及提交客服，禁止新付费与出库授权；disabled无普通登录，走恢复/支持核验。注销不能删除未交付商品或未结账务，也不能回收专属码分配给别人。清理策略按§15执行，重新注册不得凭相同邮箱自动继承已关闭账户资产。

### 22.2 邮件投递与通知闭环

Gmail、Outlook是客户的登录/收件渠道，站点发信使用企业域名和交易邮件服务，不通过客户OAuth权限读取或代发邮件。`[DEFAULT]` 邮件适配器首期采用Postmark，账号、域名验证及供应商当前接口须TASK-169实测；原Postmark/Resend二选一不再由不同agent各自选择。官方能力依据为[Postmark Webhooks](https://postmarkapp.com/developer/webhooks/webhooks-overview)，不假定发送API返回成功就代表已送达或已阅读。

`notifications`记录业务事件、用户、模板/语言、去重键和站内阅读状态；`email_deliveries`记录notification_id、收件地址版本、provider_message_id、attempt、queued/submitted/delivered/deferred/bounced/complained/unknown状态、时间与错误。`email_webhook_inbox`按供应商事件ID或稳定事件指纹去重，先鉴别并持久化后异步处理；依据供应商实际支持的鉴别机制实现，不能假定所有供应商都有相同签名头。回调不改变订单支付/库存事实，乱序退信要留历史，不能将旧submitted覆盖delivered。

发送超时结果未知时用供应商支持的查询/幂等能力核对，不支持时明确记录unknown并按可控策略补发。本站去重只能防本站重复排队，不能承诺跨网络绝对只投递一次；验证码代次和业务链接仍须单次消费，重复邮件不能重复付款/出库。发送请求已接受的邮件不能因页面刷新再次发送。

硬退信/投诉停止向该地址持续重试，客户登录后显示 `We couldn't deliver email to this address`，可按§21.5更新/重新验证地址。发信服务的suppression解除须符合供应商规则且留审计，不让客服直接清除投诉强行发送。临时失败按配置退避，超时进入人工待办；验证邮件过期即停止排队，重发生成新challenge，不发送过期码。

重要订单事件无论邮件结果如何都生成站内待办，不能以邮件已读作为客户授权。营销退订与必要交易通知分别建模；本期只发交易邮件。客户端未读角标、列表、详情深链和已解决状态一致，批量30件收货可按同一收货批次合并通知，保留每件记录。管理员邮件通道故障时仍需中文后台告警与独立监控告警通道，不能只用已经失效的同一邮件服务通知自己。

### 22.3 先有实物、后有质检单

入仓实物与付费检查任务分开。`warehouse_items(id,code,org_id可空,package_id,intake_batch_id,identity_state,condition_state,location_id,received_at,revision)`入库时即建，唯一物品码不因以后付费重发；无主件仅员工访问。`order_line_item_links(order_line_id,item_id,scope,linked_at,unlinked_at,reason)`在用户确认委托及实际识别后绑定。标准逐件检查任务必须引用实际item；草稿/付款时创建的是expected_item或委托位置，不是假装仓库已经有该件实物。现有samples作为受检实物视图时必须与warehouse_item一对一，不再另建同一件库存。

同一个包裹可拆出多件并分到同一客户多个订单，运单查到的是客户+相关订单列表；尚未映射时明确显示“识别客户，待确认委托”。实物数量、组件数和服务计费单位分别记录，套装一个委托单位含上下组件，不把拆出的两件组件自动变成两笔检查费。多件质检按客户确认的委托单位计价，物理装箱清单按实际可识别物件及组件复核。

### 23.2 页面入口和跨模块规则

- **零订单也能出库。** My items 列出已核验归属的物件、包裹、库存状态、委托关联与可执行动作。POST /me/items/{id}/dispositions 与订单内入口共享同一授权服务。未开质检单可发起保管或寄件，检查中的商品先按取消/换样流程处理，冻结件显示原因及工单。客户从 /shipments/[id] 查看此包，与订单内链接共用详情组件。收件地址、通知、账单、报价、退回重入库均可按物件或组织定位。
- **分摊只用于核算。** 一个批次生成一笔应收，多订单费用在 charge_allocations 留存分摊。默认以各单已装箱的委托单位数为权重，用整数美分最大余数法分配尾差，平局按订单ID排序。未委托件分入“未关联订单”余额，金额等于收费总额减订单分摊之和。财务汇总以收费项为键，退款沿原分摊键累计调整。客户查看每个批次的实际收费，不重复付款。
- **改数量或价格。** 接受前锁订单版本及逐行价格。缺数量档时先建有负责人和有效期的人工报价待办，由客服发布版本报价后通知客户接受。接受后部分缺件、换样、取消、重新报价必须保留 scope_revisions。补款用独立收费项，负差额预留原付款可退额度。实际到账和授权前保持新增任务阻断，其他已授权发运按物件判断。
- **确认样管理。** 在 My items 选择留为确认样，明确适用项目、保存条件、有效期、保管报价与授权。仓库记录库位、初始状态、照片及版本。新委托引用具体reference_id；出库、释放或到期与任务领取取得同一物件锁，已有任务先完结或由客户接受替代参考样。到期前提醒，更换参考样另建版本，报告保留当时对照关系。
- **报告分享范围。** AT-29 在首发按基础只读能力验收。客户主动选一个已发布版本，选择期限或撤销链接，匿名视图只展示该版获准输出的报告内容。链接每次访问校验到期、撤销与版本归属，图片走同样的访问守卫，禁止返回原图私有键及订单时间线。默认关闭对外分享，生产开启须有真实撤销验收记录。
- **异常工单有明确下一步。** PAGE-M04 要求分类、关联对象、负责人、下一次处理时间、客户可见状态及解决证据。手工报价用 POST /staff/orders/{id}/quotes 提交逐行价格、交期、原因、条款和 expires_at，返回与标准报价相同的 Quote 并要求客户接受。从询价进入订单时关联原工单。需要客户回复的退货地址/材料可从英文待办补齐。负责人交班、超时、员工停用时退回中文主管队列。未解决的资金争议、仓损、危险品锁定对应动作，客服关闭消息工单不能解除实物或财务阻断。

没有订单的人工核费、售后与报价也按已验证组织处理。客服从资金页 POST /staff/payments/{id}/refunds 发起退款，原订单入口先解析具体 payment_id 再调用同一服务；最近MFA的独立审批者锁付款记录及进行中退款，不允许申请人自批。客户从 /me/billing 和 /me/items 访问本组织费用和物件，报价待办链接 /quotes/[id]，无需拼出虚拟订单号。零价仅限明确批准的免费规则，收费服务在事务内写零额授权记录，标注免费原因及批准版本，不生成Stripe交易或虚构渠道收据。全额退款后的同笔服务不能重复履约。

收货认领提供 POST /me/intake-claims，传预报ID、快递公司、单号及购买时的发货凭证，返回私密工单号。员工核验前只显示申请进度，包裹照片、商品清单、原所有人和详细地址只在归属确认后开放。入仓轨迹允许先于质检单，但系统须检查登录用户的预报、承运商校验和异常绑定记录，仅展示脱敏经过节点，冲突或疑似枚举时暂停轨迹详情并进入核验。恢复结果以当前用户归属为准。

## 附录 C：Stripe 支付集成规格（R1 唯一收款渠道）

本附录规定 Stripe 渠道行为，内部收费及幂等边界见 §10.6。固定 SDK 与 API 版本，接入测试环境时核对商户配置。

### C.1 开户前提（阻塞项）

- **Stripe 公开资料显示不为中国大陆主体开通商户账户**（大陆客户仍可向海外商户付款）。我无法实时核实 Stripe 当前的支持名单，请以 stripe.com/global 为准。
- 本项目使用香港公司申请 Stripe 账户。正式收款须通过附录 C.10 的检查。
- 经营主体的选择同时决定税务、银行、合规、条款中的“卖方”名称、客户账单上的商户名称，应由会计与律师参与决定 `[DECIDE]`。
- 开户审核会看业务描述。提交时说明：我们销售对客户自行寄到仓库的实物样品进行检查并在线交付报告的服务；**不代收货款、不代购、不销售商品、不转运客户货款**。开户前请阅读 Stripe 的禁止与受限业务清单并确认没有冲突，我没有核实其中是否有与本业务相关的条款。
- 开户后 Stripe 可能要求补充验证，或对新账户设置储备或延迟结算，上线前要了解结算周期对现金流的影响。

### C.2 集成方式

使用 **Stripe Checkout（托管支付页）**，通过 Checkout Session 接口创建，`mode=payment`。因为价格本来就由服务端按服务、实际件数与价格版本算出，所以用**动态金额**（`price_data`），不需要在 Stripe 后台为每个 SKU 预建产品。

| 项 | 设计 |
| --- | --- |
| SDK | 官方 Node 库，版本与 API 版本在代码中固定 |
| 创建会话 | 金额从已确认收费项读取。client_reference_id=charge_item_id，metadata含payment_id、charge_item_id及org_id。收件邮箱取已验证主要邮箱。回跳/account/billing，核对本次收费状态后提供订单/发运深链 |
| 幂等 | 创建请求带 `Idempotency-Key = payments.idempotency_key` |
| 保存 | `payments.provider='stripe'`，`provider_ref` 存会话 `id`（`cs_...`），`provider_data` 存 `payment_intent` 等关键字段 |
| 回跳页 | 只做提示并轮询订单状态，**不以回跳参数放行**；付款以 webhook 为准 |
| 再次支付 | 每个收费项目同一时间只允许一个有效支付尝试（部分唯一索引，见 C.4）；会话过期或取消后，点击 Pay now 新建会话并把旧支付置 canceled |
| 币种 | 只支持 USD |
| 折扣（R2） | 在我方计价后直接写入 `unit_amount`，不使用 Stripe 的优惠券，保证价格只有一个来源 |
| 付款方式 | 在 Stripe 后台启用需要的方式（银行卡与常见钱包），不需要的关闭；延迟到账的方式要处理 C.3 的异步事件 |
| 客户显示名 | 设置 statement descriptor，例如 `QCWAREHOUSE`；以账户实际名称与规则为准 |

### C.3 Webhook 规范

- **端点**：`POST /api/v1/webhooks/stripe`，读取**原始请求体**，用官方库的 `constructEvent(rawBody, signatureHeader, STRIPE_WEBHOOK_SECRET)` 验签（默认有时间容差，防重放）；验签失败返回 401，并写审计。
- **响应**：只做“验签 → 写 `payment_events` → 投递任务 → 返回 2xx”，业务处理放 worker。
- **重复与乱序**：按 (provider,event_id) 去重；对支付、退款或争议对象读取最新渠道状态并幂等更新，分别按 charge_item、具体 refund ID、dispute ID 应用业务效果。
- **处理的事件（R1）**：

| 事件 | 处理 |
| --- | --- |
| `checkout.session.completed` | 若 `payment_status = paid`：执行下面的付款成功流程；若为 `unpaid`（延迟方式）：支付置 `processing`，等待异步事件 |
| `checkout.session.async_payment_succeeded` | 同付款成功流程 |
| `checkout.session.async_payment_failed` | 支付置 failed，收费项保持待支付，客户可重新支付，邮件提示 |
| `checkout.session.expired` | 支付置 canceled |
| charge.refunded 或 refund.updated | 对账当前 charge 下具体退款对象及状态，逐个按 refund ID 匹配；缺少本地申请则创建渠道来源记录和核对工单。仅成功对象计入已退 |
| charge.dispute.created | 按付款保存 payment_disputes，并定位收费项关联的订单、发运批次和实物。有关订单记录阻断，已结单和未委托实物仍按收费关联冻结后续交接，通知管理员 |
| `charge.dispute.closed` | 保存渠道结果。管理员核对余额和实物后显式解除相应阻断，解除前继续冻结 |

**付款成功流程**

1. 用会话 `id` 或 `metadata.payment_id` 找到本地支付；找不到则建工单，不报错重试。
2. 校验 metadata.payment_id、charge_item_id、所属组织及测试/生产环境。跨订单运费按已确认批次关联所有订单，不要求唯一order_id；校验币种为 USD。
3. **金额校验**：配置 `stripe.tax_behavior`。未启用税务或税额另计时，比较会话的 `amount_subtotal` 与 收费项快照的 USD 金额；价格含税时比较 `amount_total`。不一致则不触发 `payment_succeeded`，建工单 `payment_refund` 并通知管理员。
4. 在事务中按 §10.6 应用收费：inspection 推进订单及生成委托位置；dispatch 放行报价对应处置；storage 更新截止日。记录渠道实收和税费，不串用订单服务状态。
5. 按 payment_intent 的 charge 获取结算信息，逐支付保存真实手续费、币种、汇率；转换为 USD 后汇总到订单成本。结算尚未生成时异步补齐，不阻塞已核实的履约。

### C.4 持久化

支付尝试、收费对象唯一应用、回调及退款约束统一见 §4.2。财务按实际成功收款、退款对象及各自结算币种对账。

### C.5 退款流程（R1，通过接口发起）

1. 客户在售后页申请或客服代录；系统保存原收费对象、申请依据和金额，超管审批。
2. super_admin 批准时锁原支付并校验可退余额，见 §10.6。Stripe 请求使用原 payment_intent、批准金额、refund_id 和 charge_item_id，订单ID仅在确有对应订单时附加。
3. 批准时预留余额并持久化退款命令，worker 以 refunds.id 向渠道请求；按 refund 对象最终状态结算并发送通知。
4. 部分退款允许多次，累计不得超过实收金额；超过则本地拒绝（`REFUND_NOT_ALLOWED`）。
5. 若启用了 Stripe Tax，退款金额中的税额按比例一并退还，实际金额记入 `provider_amount_cents`。
6. **手续费**：Stripe 对退款通常不返还已收的处理费，请以其当前定价页为准；成本核算按“手续费不退”保守处理，10.3 中“支付渠道手续费由平台承担”在 Stripe 下成立。

### C.6 争议（拒付）处理

- 收到 charge.dispute.created 后冻结出库并创建高优先级工单；非终态订单进入 on_hold。管理员按渠道期限提交订单时间线、证据、报告及同意记录。
- 证据时限与争议费用以 Stripe 当前规则为准；R2 增加证据包一键导出与自动提醒。
- 未结争议冻结实物交接与结单。争议金额及手续费按渠道结算记录独立列账，并标记 dispute_id，避免与客户退款重复扣减贡献。

### C.7 税务、收据与发票

- **与 Merchant of Record 渠道不同，Stripe 不替我方处理销售税，我方经营主体是卖方，税务与合规责任在我方** `[DECIDE]`，由会计确认。
- 可选启用 Stripe Tax 自动计税，需要完成税务登记与产品税务类别设置；是否含税展示由 `stripe.tax_behavior` 决定，并影响 C.3 的金额校验。
- 收据：在 Stripe 后台启用付款收据邮件；我方订单摘要页作为补充。正式发票（R2）按经营主体要求另行实现。
- 条款与隐私政策需写明卖方主体名称、Stripe 作为支付处理方；FAQ 第 24 条已按此改写（16.3）。

### C.10 上线前检查（Stripe）

1. 账户验证完成，已确认结算币种与结算周期，银行账户与经营主体一致。
2. 业务描述与 statement descriptor 已设置；站点上有清晰的服务说明、价格、退款政策与客服邮箱。
3. 正式环境 webhook 端点已创建并选择上述事件，签名密钥已配置。
4. 受限密钥权限最小化；Stripe 后台开启 2FA，团队成员按最小权限授权。
5. 关闭不用的付款方式；检查 Radar 默认规则。
6. 用真实小额订单走一遍付款与退款（正式模式），确认到账与手续费记录。
7. 沙盒 C.9 的 14 个用例全部通过。
8. 验证正式收款关闭时，客户无法创建真实支付会话，已有草稿与待付订单可在开放后继续。


### C.12 经营主体：香港公司（已选定）

**开通顺序**

1. 注册香港公司（取得公司注册证书与商业登记证）。
2. 开立公司银行账户（或 Stripe 接受的结算账户）。
3. 以公司名义注册 Stripe 账户，完成对公司、董事与最终受益人的身份验证。
4. 配置 statement descriptor、webhook、受限密钥，完成 C.10 的上线前检查。

**Stripe 开户通常需要准备的材料**（以 Stripe 当前要求为准）：公司注册证书与商业登记证、董事与最终受益人的身份证件与住址证明、公司地址、银行账户信息、网站（含服务说明、价格、退款政策、客服邮箱）、业务描述（见 C.1）。

**需要注意的事项**

| 事项 | 说明 |
| --- | --- |
| 银行账户 | 香港银行对新公司、尤其是业务与资金在大陆的公司开户审核较严，周期不确定。是否可用数字银行或多币种账户作为 Stripe 的结算账户，要在开户前向 Stripe 与银行确认，我没有核实 |
| 币种 | Checkout 以 USD 收款；公开资料显示 Stripe 香港可结算港币或美元，具体取决于账户配置。结算币种与 USD 不同会产生换汇，成本以 Stripe 页面为准 |
| 对账 | 每笔 `balance_transaction` 记录结算币种、金额与汇率；R1 把 `settlement_currency`、`settlement_amount`、`exchange_rate` 写入 `payments.provider_data`，用于财务核对 |
| 卖方信息 | 条款、收据、网站页脚统一显示：公司全称、注册地址、商业登记号、客服邮箱；对应配置 `legal.entity_name`、`legal.entity_address`、`legal.br_number`，FAQ 第 24 条的 `{{legal_entity_name}}` 取自此处 |
| 仓库地址 | 服务场所是大陆仓库，条款须如实写明；公司注册地址与仓库地址不是同一地点是正常的，但要一致披露 |

**必须由会计与律师回答的问题 `[DECIDE]`**

本规格不对法律与税务做判断。以下问题在收款上线前应有书面答复：

1. 香港公司对海外客户收取服务费，而检查服务实际在广州仓库由家人完成，这种安排在大陆是否构成需要登记的经营活动，是否需要大陆的运营主体（例如个体工商户或公司）与香港公司签订服务协议？
2. 香港公司的利润在香港与大陆各自如何纳税？是否存在需要申报的情形？
3. 款项从香港账户回到大陆个人或大陆主体的合规路径，以及外汇规定。
4. 员工与家人的用工、报酬与社保安排。
5. 仓库场地的使用与对外营业所需的登记（与 18.1 第 3 项合并处理）。
6. 向不同国家客户提供服务时，是否有目的地国家的销售税或增值税登记门槛（影响是否启用 Stripe Tax 与价格含税展示，见 C.7）。

## 附录 D 仓库操作、运营指标与旧稿迁移

### D.1 仓库培训与交接

#### SOP 1 作业前标准化布置

- 工作台分区：待入库、待检查、正在检查、已检查待处置、确认样保管、异常隔离。
- 确保桌面清洁，准备软尺、直尺/测量尺、电子秤、标签打印、固定拍摄支架、适当光源和背景。
- 每天检查设备电量、刻度完整性、光源状态，记录异常；不能用损坏或未经确认的工具得到精确数据。
- 私人住宅收货需要先核实当地合法经营条件、物业、消防及承运商规定；不应在营销公开家庭地址，注册后向该账户展示后台默认地址和专属码。

#### SOP 2 每单完整 SOP

| 步骤 | 操作 | 必须留下的证据 | 常见错误及预防 |
|---|---|---|---|
| 1. 入仓 | 扫运单、拍外箱、创建入仓记录 | 运单、时间、外箱图 | 漏拍破损、未匹配客户 |
| 2. 开包 | 核对样品数量和预报 | 开箱过程图/视频（按政策）、物品清单 | 混样、误扔吊牌 |
| 3. 标签 | 贴内部样品码并登记库位 | sample_id、库位 | 仅用手写供应商名 |
| 4. 预处理 | 平铺/按约定整理、确认测量姿态 | 样品正反面图 | 拉扯衣物导致误差 |
| 5. 测量 | 按统一位置逐项测；可疑值复测 | 数值、单位、位置图 | 测量点不统一、单位混用 |
| 6. 做工视检 | 对重点位置逐项检查 | 问题特写与位置说明 | 只写“很好/很差” |
| 7. 对比 | A/B/C 同条件并排 | 并排图、差异表 | 不同光照下比颜色 |
| 8. 清单检查 | 检查必填项与照片 | 系统完成状态 | 漏项却发布报告 |
| 9. 二次复核 | 复核 sample_id、数据和越界措辞 | 复核时间、操作人 | 错样、错误数值 |
| 10. 暂存/出库 | 依客户单件处置指令 | 打包图、重量、运单 | 寄错集运仓/漏会员码 |

#### SOP 3 测量标准化与校准

- 一种品类只有一个主测量图；每个测量点定义起点、终点、平铺方式、是否拉伸。
- 两次测量差异超出内部预设阈值（例如 0.5cm，**仅为待验证管理阈值**）时要求复测；柔性服装允许何种误差需要按部位和实际材质制定。
- 尺码表属于参考信息；若客户未提供明确允许偏差，只报告测量值及差值，不擅自出“合格”。
- 对需较高精度的客户，先评估设备、方法和能力，再决定是否接受。

#### SOP 4 色差 SOP

- 同组样品放在同一可控照明条件下，并排观看；摄影使用固定白平衡或统一设置，避免让摄像头自动算法制造假的一致性/差异。
- 图片需声明“照片受不同屏幕与显示设置影响”；如果视觉存在差异，描述部位和观察光源。
- 如果使用标准光源箱，记录型号、使用光源类别、使用状态；仅在取得相应标准方法与训练后才能宣称“按照某规范执行”。
- 不用数码照片的 RGB 值冒充专业色差 ΔE 测量结果。

#### SOP 5 服装瑕疵记录的内部级别（非官方认证）

- `Attention`：观察到差异，可能需要客户确认，例如轻微线头、细小颜色变化。
- `Material Issue`：明显破洞、严重污渍、大幅尺寸差异（有客户公差时可标数值）。
- `Uncertain`：由于光照、缺少规格或方法限制，无法判断。

这些只作为客户阅读优先级，不代表 AQL 的 Critical/Major/Minor 统计等级，除非后期另建正式检验标准。

#### SOP 6 非正常情况处理 SOP

- 快递破损或潮湿：先拍摄并隔离，按保险、物流索赔与客户同意流程处理；不擅自报废。
- 发来电池、液体、危险品或疑似侵权货：暂停接收/寄出并按法律、承运商要求处理；不得自行处理危险物。
- 收到与客户预报不一致的商品：等待书面确认，不擅自替换为其他样品。
- 检查中操作造成商品损坏：立即冻结报告、完整留痕、通知客户并按赔偿规则处置。
- 样品超期：多次提醒、预留合理宽限；处置方式依据客户授权与适用法律，不得自动占为己有。


国内退货由客户在卖家平台申请，提供商家指定的有效寄回地址，并自行承担退货运费。系统记录单件授权、时限、打包证据、运单与交接点，仓库负责到约定国内交接点；客户自行处理与卖家的退款。寄集运仓必须录会员码并确认接收第三方寄件；承运商退回后重新入库并发客户待办。例外事项走系统工单。

### D.2 小规模运营验证

| 维度 | 指标 | 为什么重要 |
|---|---|---|
| 需求 | 每月陌生付费客户数 | 避免只靠内部/熟人订单 |
| 获客 | 综合 CAC（广告＋佣金＋人员获客工时） | 低频服务的生死线 |
| 收入 | 服务收入、订单均价、附加服务净收入 | 区分质检收入和代收运费 |
| 成本 | 直接人工分钟、管理/客服分钟、耗材 | 不把家庭人工视为零 |
| 运营 | 错件率、报告修订率、超期订单率、样品丢损 | 可靠性决定是否能扩大 |
| 客户 | 是否再次委托、是否引荐他人、是否保留参考样 | 不只看 60 天复购 |
| 物流 | 订单到货齐套时间、出库交接差错 | 真正的体验瓶颈 |
| 现金流 | 预收待履约金额、退款负债、合作商未结佣金 | 不能把预付款全部视作利润 |


首批按 5、20、30 单复核。记录每步工时、客服工时、异常、修订、真实获客成本、支付费与贡献；区分真实买家与内部订单。严重重复错样或报告事实错误时暂停扩量，由业务负责人核对 SOP 和证据。
